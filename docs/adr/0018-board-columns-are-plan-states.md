# Board columns are Plan Item states, so PlanState grows to six

The **Board**'s six **Columns** — `backlog`, `ready`, `active`, `blocked`, `review`, `done` — are not a separate concept layered over the plan: they *are* the item states. `PlanState` gains `backlog`, `ready`, `blocked` and `review` alongside the existing `active`, `done`, `failed` and `dropped`. Moving a card is a state change and nothing else. **Groomed** (specified enough to start, nothing blocking) is what promotes `backlog` → `ready`. The implicit WIP limit of one `active` item is kept, with its existing silent demotion; `blocked` and `review` are uncapped holding areas.

**Considered.** *A sidecar file* mapping item IDs to board columns leaves the plan schema and its ADRs untouched, and was rejected because two files would then describe one item and could disagree — the exact failure the single-file format was chosen to avoid. *Encoding the column as a tag in the item's text* was cheapest and rejected as abusing free text for structured data, made worse by `revise` rewriting that text. *Dependency-derived readiness* (`ready` = all dependencies done) is mechanical and needs no judgement, but the model has no dependency edges between items and inventing them is a much larger change. *Collapsing backlog and ready* was the honest simplification and was declined.

**Consequences.** Old builds reading a new plan file will see unrecognised states, and degrade them to `pending` rather than dropping the line — the format was already forward-compatible in this exact way, and this decision depends on that behaviour. Note that `pending` itself is now the odd one out: it is the legacy name that `backlog` and `ready` split, and files written by older builds will contain it. "Blocked" is now overloaded against herdr's own detected `blocked` pane state; they are unrelated, and a Run can be herdr-blocked while its Item is `active`. The terminal-state set is unchanged, so adding four states does not change what archiving means.
