# Spawning pi requires proving the target is pi

A process that re-invokes "itself" must establish *what* itself is. `getPiInvocation` in the subagent extension re-executes `process.argv[1]`, which is correct there because that extension only ever runs inside pi, so `argv[1]` **is** pi. The plan extension's copy inherited that assumption and broke it: `review.ts` can also be imported by a test harness, and then `argv[1]` is the harness. "Spawn pi to review this item" silently became "re-execute the calling script" — which imported the module again and spawned again, at roughly four processes per second, 90 of them before the user killed everything to recover 31GB of RAM.

The fix is that a spawn target must be *identified*, never assumed. The current script is reused only when it looks like pi (`pi`, or `pi.ts`/`pi.js`/`pi.mjs`/`pi.cjs`); a non-generic `execPath` is trusted as a compiled pi binary; otherwise a `pi` executable is located on `PATH` by an explicit `X_OK` check. When none of those identify a pi, `getPiInvocation` returns **null** and the review is reported as a **Dead review** rather than a guess being executed. Refusing to run is always recoverable; executing the wrong thing is not.

Three faults had to line up, and each was independently sufficient to prevent the disaster, which is the real lesson: every one of them was believed safe.

**The interlock was in the wrong place.** `PI_PLAN_IN_REVIEW` was checked in `dispatchReview`, the *policy* layer, and not in `runReview`, the layer that actually spawns. A harness calling `runReview` directly never met the guard. A guard that the spawning function does not itself apply protects only the callers who remember it — the same honour-system shape [0032](./0032-autonomous-mode-defaults-the-review-route.md) rejected for the forgotten `attach`, reintroduced by accident one layer down. The check now sits at the spawn, where it cannot be routed around, *in addition to* the call site.

**An empty string is falsy.** The child's `PI_PLAN_KEY` was cleared with `""` to stop a review adopting the plan it was reviewing. But the plan extension decides "am I a main session?" with `!process.env.PI_PLAN_KEY`, so `""` made every review child believe it *was* the main session: it restored the plan, re-injected it into context, and (in a TUI) would spawn a Board. Clearing a variable and setting it to a sentinel are different operations, and the code needed the second. It is now `__review__` — non-empty, and not any real plan key, so `planFileFor` resolves it away from the reviewed plan.

**Nothing bounded the blast radius.** Both faults above were reasoned about and believed correct; neither was. So `runReview` now enforces `MAX_CONCURRENT_REVIEWS = 3` as a backstop against the *next* fault of this class, turning any runaway into a handful of wasted processes rather than an unbounded one. Building it surfaced a further bug of exactly the kind it exists to catch: the counter was incremented at the spawn, three `await`s after the check, so twelve concurrent callers all passed the cap check before any of them counted it — twelve spawns against a cap of three. The slot is now claimed synchronously with the check, before any `await`, and released in a single `finally` covering every exit, because a leaked slot would silently shrink the cap toward zero until no review could ever run again — a quiet failure worse than the noisy one being guarded against.

**Considered.** *Keeping `argv[1]` and documenting the hazard* was rejected because the hazard is invisible at the call site and its failure mode is machine-wide. *Importing the subagent extension's `getPiInvocation`* would create exactly the dependency ADR 0032 keeps out, and would propagate the same unsafe assumption rather than fix it. *A hard-coded absolute path to pi* breaks on every install layout. *A lock file to prevent concurrent reviews* solves a narrower problem than the counter and adds the stale-lock class of bugs already fought in [0035](./0035-contended-plan-lock-refuses.md). *Detecting recursion by process ancestry* (walking parents looking for pi) is far more machinery than an environment flag, and the flag was never the weak part — its placement was.

**Consequences.** A review now refuses to run in three new situations: inside another review, when pi cannot be identified, and when three are already in flight. All three surface as Dead reviews, which leave the Item in `review` with the reason in its note and spend no **Review Budget**, so refusal costs a retry rather than a wrong Verdict. The cap is per-process and deliberately not configurable, since a user who needs more than three concurrent oracle reviews has a scheduling problem the plan extension should not solve. Finally, the subagent extension's `getPiInvocation` still uses the bare `argv[1]` form: it is safe *there* under an assumption that is true today and unenforced, and this ADR is the record of what happens when that assumption travels.
