# One spawn cap for every child

> **Amended by [0044](./0044-native-runs-herdr-owns-the-process.md).** This ADR's own closing sentence — "the cap is per-process and dies with the orchestrator, which is correct while children cannot spawn and wrong the moment they can" — is now the operative one. A **Native Run** is a full `pi` with the subagent extension loaded, so it can spawn, and nested Runs are native too. The module-level counter must become tree-wide, in the lock-directory shape of [0035](./0035-contended-plan-lock-refuses.md), exactly as anticipated here. _[Done: the counter now lives in a `.spawn-cap` directory of pid-stamped tokens shared by every pi in the tree, and the grant this ADR told us to guard was made only after that was measured — a second process saw the first's five slots, took the sixth, and was refused the seventh.]_

Three separate limits guarded process spawning, and together they guarded nothing. The subagent registry admitted 6 Tasks; the review dispatcher allowed 3 concurrent reviews; a Rework worker would have brought a third counter. The oracle review that raised this flagged the missing Rework cap, and measuring the existing ones turned out worse than the report: **a Task is not a process.** A parallel Task runs up to `MAX_CONCURRENCY` (4) Runs at once, so six admitted Tasks are up to twenty-four children, plus three reviews — twenty-seven concurrent pi processes while every individual cap reported healthy. A comment in the subagent extension asserted the opposite, that "the ceiling on total load is MAX_ACTIVE_TASKS", which was false in the way that matters: it was the reason nobody looked.

So there is now one counter, in `subagent/spawnlimit.ts`, claimed per **child** rather than per Task, capped at 6. There is one machine and one RAM budget; a limit that counts only some spawns bounds nothing. Tasks, autonomous reviews and any future Rework worker draw from the same pool and compete for it, and a refusal names who is holding the slots so the message is actionable rather than merely a denial.

**The cap sits at the spawn site, not at admission.** `MAX_ACTIVE_TASKS` stays where it is as a Task-level shaping limit — it bounds how much work is *in flight*, which is a different question from how many processes exist — but the process cap is claimed inside `executeAttempt`, wrapping the one place a child is actually spawned. Counting Runs is counting processes; counting Tasks is not.

**`claimSlot` is synchronous, and that is the whole design.** The first version of the review cap checked the counter and then incremented it three `await`s later, so twelve concurrent callers all passed a cap of three — a check-then-act race inside the mechanism meant to prevent runaway spawning, in code written days after a fork bomb. Making the claim synchronous with the check removes the gap structurally instead of asking each caller to be careful, and `release` is idempotent so a caller that releases on both a normal and an error path cannot quietly enlarge the budget.

**A module-level counter is sufficient here, and that rests on a checked fact.** Both spawners run in the orchestrator's process, and a child cannot spawn: children are launched with `--tools` from their agent file, and no agent in `agent/agents/` lists `subagent` or `plan`. So no child holds a tool that could delegate or dispatch a review. If an agent is ever granted one, this stops being true and the cap must become cross-process — a lock directory, as in ADR 0035. That grant is the thing to guard, and it is recorded in the module so the next reader meets the assumption rather than inheriting it silently.

A refused Run is not a wedge. It is marked `stopReason: "error"` with the refusal as its `errorMessage`, so the unified `runFailed` predicate classifies it as failed, the registry reaches a terminal state, and a Reminder fires — verified, because a refusal that left a Run pending forever would recreate the bug ADR 0033 fixed. A refused review is a **Dead review**: it spends no **Review Budget** and is simply worth retrying, consistent with every other refusal-before-start.

**Considered.** *Keeping per-kind caps with a documented aggregate* was the cheaper option and was rejected because the aggregate was already documented — wrongly — and nobody noticed for as long as the comment existed; a number that must be maintained by hand across three files is a number that will drift. *Raising the cap to cover the true worst case* answers the wrong question: twenty-seven children is not a limit anyone chose, it is arithmetic nobody performed. *Making the cap configurable* was rejected because a plan needing more than six concurrent children has a scheduling problem a bigger number will not fix. *A queue instead of a refusal* is the friendlier behaviour and was rejected for now: a queue needs fairness, cancellation and a wait mechanism, whereas a refusal is honest, visible and retryable — and for autonomous reviews the retry already exists.

**Consequences.** A Task can now be admitted and still have a Run refused a slot, so admission no longer implies execution — callers must read the Run's outcome, not the Task's acceptance. Six concurrent Runs is a real reduction from the previous unmeasured worst case, so a wide parallel Task will now serialise more than it used to; that is the intent. The cap is per-process and dies with the orchestrator, which is correct while children cannot spawn and wrong the moment they can.
