# Review Routes: the agent chooses who clears each Plan Item

> **Status: implemented.** The `route` field, the `route` op with its ratchet,
> route-aware `done`, and the Board's per-card glyph are all in place. What is
> *not* yet built is the automation on top: nothing dispatches an oracle review
> or reads a **Verdict**, so an `oracle`-routed Item currently sits in `review`
> until the user accepts it. See [0032](./0032-autonomous-mode-defaults-the-review-route.md).
>
> **Amended by [0032](./0032-autonomous-mode-defaults-the-review-route.md)** on
> one point: the `unsure` **Verdict** no longer escalates to `user` on the first
> occurrence. It returns the Item for **Rework** exactly as `fail` does, and
> reaches the user only once the **Review Budget** is spent.

Supersedes [0017](./0017-done-means-accepted.md). Every **Plan Item** carries a **Review Route** — `user`, `oracle`, or `skip` — chosen by the orchestrator when the Item is **Groomed** (`backlog` → `ready`). `done` no longer means "the user accepted it"; it means the Item's route was satisfied. A `user`-routed Item still reaches `done` only by the user's hand via `/accept`; an `oracle`-routed Item is cleared by a `pass` **Verdict**; a `skip`-routed Item goes `active` → `done` directly and never enters `review`, because `review` is the column for Items awaiting a reviewer and a skipped Item has none.

The route is a new optional field on `PlanItem`, absent meaning `user`, so existing plan files and older builds keep today's behaviour exactly — an upgrade never silently starts auto-clearing anything. Routes move in one direction only: `skip` → `oracle` → `user`, via a dedicated `route` op that enforces the ratchet. This is the anti-gaming property that makes grooming-time selection worth anything: an agent that discovers its work is hairier than groomed may always ask for more scrutiny, and can never award itself less once it knows how painful review would be. Triviality is the orchestrator's own judgement and is never referred out; an orchestrator *unsure* whether work is trivial routes to `oracle` rather than skipping, so uncertainty resolves to more scrutiny by construction. Oracle therefore only ever judges correctness. Its **Verdict** is a fixed token in its **Write-up** (`pass` / `fail` / `unsure`) rather than prose to be interpreted, so the orchestrator cannot re-litigate a rejection it dislikes: `pass` → `done`, `fail` → back to `active`, `unsure` → escalate to `user`. A review **Task** that dies without a verdict is not a verdict — the Item stays in `review` and the review is retried once; a second failure escalates to `user` with the reason the reviews failed. The user may `/accept` any Item in `review` whatever its route: a route binds the agent, not the user.

**Considered.** *Keeping `done` = user-accepted and adding a sibling terminal state* for auto-cleared work keeps `done` from ever lying, and was rejected because it splits the terminal set and grows the Board to carry a distinction the route field already records. *A plan-level route* is what was originally asked for and was rejected because `review` is a per-Item column: one route for a whole plan forces a risky Item and a typo fix down the same path. *Choosing the route at completion* rather than at grooming has strictly better information and strictly worse incentives — the agent picks its reviewer after learning how much scrutiny it wants — so the worse-informed, better-incentivised timing won. *Mechanical criteria for `skip`* (no writes, single file, no shell) are un-gameable but blunt: a one-line auth config change passes every test. *Oracle gating each skip decision* costs a round trip on exactly the Items skipping was meant to make cheap. *Encoding the route in the existing `note` field* avoids a schema change and was rejected for the same reason 0018 declined to encode columns in item text: unstructured free text the user also writes into.

**Consequences.** A plan can now be born, worked, cleared and archived without the user ever seeing it — precisely the outcome 0017 preserved the self-archive rule to prevent. That is accepted deliberately, and the archived plan records each Item's route so it is always auditable after the fact which Items cleared themselves and how. The footer's progress count no longer measures acceptance. `done` stops being a single claim and must be read together with the route, so any consumer treating `done` as "a human signed this off" is now wrong. The `done` policy was one constant and one guard (`AGENT_SETTABLE`, and the refusal in the `status` handler); it becomes route-aware, which means the guard now needs the Item's route in hand to decide legality — a state change is no longer judgeable from the target state alone. `/accept` remains a writer of `done` but is no longer the only one.
