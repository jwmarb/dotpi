# Attempt identity comes from the filename, and the parent announces the session it finds

Four defects in how a Run's session file is identified, all downstream of one mistake: [0025](./0025-mirror-resolves-its-own-session-file.md) removed the parent's discovery deadline — correctly, it was a race the child could lose — but replaced it with a heuristic, and never replaced what the deadline had been *feeding*.

**A Mirror Pane could not follow a model fallback.** `resolveFile` latched the first `.jsonl` it saw and never moved. Every fallback attempt re-runs with the same `runId`, session directory and `--session-id`, writing a *new* timestamped file, so a viewer that latched attempt 1 showed a frozen transcript for the rest of the Run and the fallback's turns were never displayed.

**Attempt identity is the filename, not mtime.** Both orderings were tried and both were wrong on their own. Filename-sort alone cannot tell attempts apart — it was only ever "latch the last one". Sorting by mtime looked more principled and was worse: thawing an archived earlier attempt rewrites it *now*, giving the oldest attempt the newest mtime, which walked the viewer backwards mid-Run and reprinted an old transcript as if new. My own test caught that, after I had already written the mtime version and called it the fix. Every session file is `<iso>_<runId>.jsonl` — verified across all 19 on disk — so the filename is the one value that says *which attempt* a file belongs to, and mtime only says when bytes last moved. Latching is now strictly forward: a newer attempt is followed, an older one is ignored.

**The parent never learned the session path at all.** `openMirrorPane`'s only `reportAgentSession` call is guarded by `sessionFile`, which comes from `thawRun` — and `thawRun` only finds an *existing archive*. For every fresh Run it is `null`, so herdr received no session path and `run.sessionFile` stayed unset for the Run's whole life. The viewer resolved the file seconds later and told nobody. ADR 0025's claim to have removed a *class* of race was therefore only half true: it removed the deadline, and left a one-shot discovery that fresh Runs always lose. The parent now watches for the first write in the background — no deadline it can fail, since the pane renders regardless — and publishes the path when it appears.

**"Waiting for the run to start…" was sometimes a lie.** The viewer holds file state but no lifecycle state, so a Run that died before its first write, or a directory it cannot read, looked exactly like a slow start and sat there reassuringly forever. Run Meta now carries an `outcome` field (`running` / `completed` / `failed`), written in `executeAttempt`'s `finally` so even a thrown Run records one, and the viewer says what actually happened. It stays silent when waiting is still honest: a genuinely slow start, a directory not yet created, or an older Run whose sidecar predates the field — no guessing.

**Task IDs were too small to be unique on disk.** `randomBytes(2)` gives 65,536 values, and `mintId` checked only the in-memory registry — which dies with the orchestrator ([0001](./0001-tasks-die-with-the-orchestrator.md)) while Run directories live 90 days. A reused ID means a reused directory, which is the same bug as the fallback one: a viewer bound to another Run's evidence. Measured against retained Runs, the chance of *some* collision was 1.9% at 50, 26% at 200 and 85% at 500. Four bytes make those 0.0000%, 0.0005% and 0.003%, and `mintId` now also rejects IDs already present on disk, computed once after reaping so deleted Runs stop reserving theirs.

**Considered.** *Per-attempt subdirectories plus a manifest* is the structurally clean answer and what an oracle review recommended: identification becomes a fact rather than an inference. It was rejected as too large for now — it changes the layout that reaping, thawing, reopening and the Board all read, and needs a migration for existing flat directories. The filename already encodes the attempt, so the cheap fix is available; the manifest remains the right move if a second ambiguity appears. *Having the child announce its session path on stdout* would be authoritative, and the child does emit a `session` entry — but only *into the file*, which is circular for a reader trying to find the file. *Having the parent pre-create the file* was rejected because nothing in the CLI contract says the child will adopt a caller-chosen path. *Raising the old discovery timeout* is what 0025 already rejected, and rightly. *Deriving the outcome from the session file* instead of a sidecar cannot work for the case that matters: the file does not exist. *Eight-byte Task IDs* remove all doubt and double the length of an ID the user types by hand in `/run`.

**Consequences.** The viewer can now switch files mid-Run, which means `printed` — the load-bearing line count of an append-only stream ([0029](./0029-mirror-panes-are-append-only.md)) — is reset on a switch and a `— new attempt —` divider is printed; a bug that made two attempts render as one stream would now duplicate output rather than merely stall. `run.json` grows from decoration into state a reader acts on, so a *failed* sidecar write is now a small loss of truth rather than only of labelling. Task IDs get longer, and older Runs on disk keep their four-character IDs, so both lengths coexist — anything parsing an ID by length is wrong. The background session watcher is one more timer per Run, bounded at five minutes and cancelled as soon as the Run ends. Finally, the fallback fix is verified against a *model* of the resolver rather than a live fallback: no real fallback has been observed end to end, because forcing one needs a model that fails on demand.
