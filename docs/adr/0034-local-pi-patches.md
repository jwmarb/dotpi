# The installed pi package is patched locally, and the patch must be re-applied after every update

Three changes live **outside this repository**, in the installed `pi` package. The first two are about retry and are load-bearing for session survival; the third is cosmetic and came later (see the amendment at the end):

1. `"upstream request failed"` is added to the retryable-error list. The user's gateway is litellm, which returns **HTTP 400** for an upstream failure (`litellm.BadRequestError: OpenAIException - Upstream request failed`). pi classifies 400 as permanent, so a retryable gateway blip ended the session for good: chat stopped forever and no retry was attempted.
2. The outer retry ladder is capped: `Math.min(baseDelayMs * 2**(n-1), maxDelayMs ?? 128e3)`. It had **no ceiling**, so the ten retries the user asked for would have reached 8.5- and 17-minute waits, a 34-minute worst case. `retry.maxRetryDelayMs` in `settings.json` does not do this — it belongs to the provider SDK, not this loop — so the ceiling had to be code. `agent/settings.json` supplies `maxRetries: 10` and a new `maxDelayMs: 128000`, giving 2, 4, 8, 16, 32, 64, then 128s four times: 10.6 minutes worst case.
3. `setHiddenThinkingLabel` is scoped to one message. See the amendment below.

**No extension can do this.** Retry classification is not exposed: `after_provider_response` carries a status but has no result type, `message_end` has no result type either, and no extension receives a handle to the `AgentSession` whose `_isRetryableError` decides. An extension-based fix was recommended, then retracted as impossible. Patching the package is the only mechanism available, which is why this ADR exists at all — it is not a preference.

**The target is a bundled chunk, not the file that looks right.** The first patch went into `@earendil-works/pi-ai/dist/utils/retry.js`, which is **never loaded**: the retryable list is inlined into `dist/bundle/chunks/chunk-*.js`, and `cli.js` loads that. The loose file was verified 9/9 by direct import — a meaningless result, since nothing executes it. Three oracle Runs then died on the same 400 with zero `auto_retry` events, which is how the mistake surfaced. **Anyone re-deriving this patch must confirm which file the running process actually loads**, by finding the chunk that contains the pattern rather than the module that appears to own it. The chunk's hash changes between releases, so it must be found by content (`provider.?returned.?error`), never by name.

**`scripts/patch-pi.sh` is the artefact that matters more than this document.** A note saying "remember to re-patch" fails the moment it is forgotten, and the failure is silent until chat dies mid-session. The script locates the chunk by content, is idempotent (each patch skipped when already present), backs up before writing, and exits non-zero with a specific message when an anchor no longer matches — which is the signal that upstream changed the code and this ADR needs revisiting. It was verified against a simulated fresh install under a *different* chunk hash: both patches applied, and the result classifies the litellm 400 as retryable while still refusing `401` and an oversized-image 400.

**This contradicts [0008](./0008-retry-backoff-is-configured-not-reimplemented.md)**, which says retry is handled "entirely" by stock `AgentSession` and configured through settings. That is no longer true: the installed runtime is a locally maintained fork in two small places. 0008's *intent* survives — this extension still implements no retry loop of its own and there are still no two racing backoff schedules — but its stronger claim is now false and is marked as amended.

**Considered.** *Reporting it upstream and waiting* is correct and should still happen, but leaves chat dying in the meantime; the patch and a bug report are not alternatives. *Treating all HTTP 400s as retryable*, which the user explicitly approved, was **not implemented**: the patterns are joined by bare alternation with no word boundaries, so `"400"` also matches incidental digits — `image exceeds 8400000 bytes`, `you used 140047 tokens`, `tool schema invalid at line 400` — each of which would burn the full ladder on a request that can never succeed. Every 400 in the user's history carries the "Upstream request failed" wording, so matching the wording covers the real case with none of that risk; the deviation was reported rather than made silently. *Vendoring the whole package* would make the change durable and turn every upstream update into a merge. *A `postinstall` hook* cannot help: `pi` is installed globally by `bun`, not as a dependency of this repo. *Patch-package* is the conventional tool and assumes an npm-managed dependency tree this setup does not have. *Pinning the pi version to prevent silent reversion* trades one silent failure for another — staleness instead of breakage.

**Consequences.** Every `pi` update reverts all three patches and the first symptom is chat dying permanently on a gateway blip, so `scripts/patch-pi.sh` must be run after every update; that obligation is recorded in `PATCHES.md` at the repo root, because an ADR is not somewhere anyone looks while updating. The script is a second thing to maintain: if upstream renames the settings key or restructures the ladder, its anchors stop matching, and it is written to fail loudly rather than silently no-op. The 128-second cap is now split across two places — the formula in the patch and the value in `settings.json` — so raising `maxDelayMs` alone works, but only while the patch is applied. Finally, one open coupling: the 20-minute stall timeout in [0033](./0033-parent-owns-run-termination.md) is derived from this ladder's 10.6-minute worst case, so changing `maxRetries` or `maxDelayMs` without revisiting that constant will start killing Runs that are legitimately retrying.

**Amendment: patch 3, per-message thinking labels.** With `hideThinkingBlock: true`, pi collapses each thinking block to a one-line placeholder whose text an extension sets via `ctx.ui.setHiddenThinkingLabel()`. `agent/extensions/thinking-indicator.ts` uses it to record `"Thought for 12s (ctrl+t to expand)"`. Upstream the setter **fans out to every `AssistantMessageComponent` in the chat container**, so every finished turn in the transcript is restamped with the newest duration — each turn claiming a number that belongs to a different turn.

*No extension can fix this*, for the same structural reason as the retry patches: the label is already stored per-component, but the only exposed entry point takes a string and chooses its own targets. An extension cannot name a message. `registerMarkdownTransformer` looked like the escape hatch and is not one — the collapsed placeholder is built as a plain `Text`, while transformers only run through the `Markdown` component used for *expanded* thinking, so a transformer never sees the line that needs changing.

The patch narrows a call *with* a label to a single component: the streaming one, or the newest assistant message when the stream has already ended (pi clears `streamingComponent` at `message_end`, before an extension's own `message_end` handler runs — so the fallback is what makes the common path work at all). A call with **no** argument keeps its original meaning, resetting every component to `"Thinking..."`; pi itself makes that bare call on `/reload`, so preserving it is not optional. The patched code deliberately does **not** write a per-message label into `this.hiddenThinkingLabel`, because that field seeds newly constructed components — persisting it would make the next turn open already displaying the previous turn's duration while it is still thinking. Both of those were real bugs in earlier drafts of the patch, caught by an executable model of the setter that is checked against the unpatched code as a negative control: unpatched, three of its six assertions fail.

*Considered.* **Living with the global label** is the honest zero-risk option and was the state before this patch; it was rejected because a duration attached to the wrong message is worse than no duration — it is confidently wrong. **Dropping the duration entirely** and keeping only the live widget avoids the patch but loses the record as soon as the turn ends, which was the point of putting it in the transcript. **A per-block label API** is what upstream should expose, and is the right bug report to file; unlike the retry patches, nothing breaks while waiting, so this one is genuinely optional. Weigh that when re-deriving anchors after an update: if this anchor alone fails, the correct response may be to drop the patch rather than fight for it.
