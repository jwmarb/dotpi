# Every Run carries its own Plan

**Status:** accepted

The planning machinery (Plan, Plan Item, Board, Starter Plan) was built around the orchestrator's session. A delegated Run's child is a full `pi` session that loads the same user extensions, and the spawner already hands it a plan key (`PI_PLAN_KEY` = Task ID, `.rN` for parallel Tasks) that the child's plan tool resolves — but seeding a child's plan was a prompt convention on the orchestrator, plan-spawned `pln-` Runs all shared one sentinel key (`__review__`) and so addressed one shared plan file, and the parent's Board read the Runs' session directories for progress without ever reading a child's plan file. The answer to "what is this Run working through" therefore lived only inside the Run's own pane (a footer and a widget the LLM cannot see), not on the kanban the user watches.

**Decision:** every Run has its own Plan, and the spawner seeds it at spawn when it is handed starter items. A Run spawned without a starter list is not seeded: its plan file is created by the child's own plan tool on first use, under the same Task ID key, and the Board card carries no plan items until the child records some. The slot is always the Run's; the contents are never invented.

- *Delegated `sub-` Runs.* The `subagent` tool gains a `plan` parameter (a list of item texts, per Run). The spawner seeds the child's plan file in the same code path that already computes the plan key — locked, never-clobbering, best-effort: a pre-existing file means the seed is skipped and the spawn proceeds. A Run spawned without the parameter, or with an empty list, is seeded with nothing — the child's plan tool creates its plan file on its first write, as it already does for any `PI_PLAN_KEY`-keyed session, and the spawn is unchanged. When items are seeded, a fixed one-line nudge is appended to the delegation brief ("Your plan is seeded with N items — maintain it as you work"), because the child's plan is deliberately not injected into its context (the `PI_PLAN_KEY` branch of session start) and the nudge is the bridge.
- *Plan-spawned `pln-` Runs.* The per-Run plan key becomes the Run's own runId; the shared `__review__` sentinel is retired (its contract — non-empty, and not the reviewed plan's key — is preserved by the runId). The spawner seeds Rework Runs with oracle's findings as items (split on bullets/blank lines; when that yields a single block, the findings seed one item plus verify and commit) and review Runs with a single item. Seeded items carry route `skip`: the child is the worker and cannot `/accept` its own items, and a `user`-routed item would block the child's `done`.
- *The Board.* A card carrying a Task ID now lists the Runs' own Plan items — read from each Run's plan file (`plans/<taskId>.jsonl`, `.rN` variants, the item's `reworkRunId`, and the review Run's ID, which is recorded on the Plan Item beside `reworkRunId` for exactly this purpose) — with done items dimmed. The plan file is the single source of truth, live and post-hoc; no plan snapshot joins the Run directory.

**Considered options.**

- *Keep seeding as the `plan op seed` convention.* No tool change, but seeding depends on orchestrator memory and the brief and the list can drift apart; the parameter puts the seed in the code path that already owns the key.
- *A plan snapshot in the Run directory, like `prompt.md`.* A second copy that goes stale while the Run is alive; the plan file is already keyed and discoverable, and the Run directory contract keeps its stated scope (ADR 0045, ADR 0047).
- *A fixed seeded checklist for review Runs.* Prescribes the oracle's working method; its judgement is meant to be its own reading of the work, and it may split its own plan freely.
- *Compact counts on the card (e.g. `plan 2/5`).* Scannable, but the user watching the Board wanted to see what each Run has outstanding, not a ratio.

**Consequences.** The `__review__` plan file is orphaned once the key moves — no reader addresses it, and pre-existing ones are left in place. The review Run's ID joins the Plan Item (beside `reworkRunId`) so the Board can read a review Run's plan; without it, a review Run's plan would be findable only by parsing the Item's note. The nudge line crosses inside the brief text, so ADR 0047's verbatim-no-prefix decision is unchanged — it is part of the brief, not a second channel. Fallback (piped) Runs, which have no TUI of their own, gain live plan visibility through the Board card, which refreshes against the file. Nested Runs are uniform: a grandchild gets its own plan file, keyed under its own Task ID by the child's own spawner, and is seeded only if that spawner hands it items. The one deliberate exception to "routes are the orchestrator's, chosen at grooming" is the seeded `skip` route: a child's list is a tracking aid, not a review contract, and the parent's Items are untouched. Dimming on a card now has a second use — done child-Plan items — which amends ADR 0043's "only dimmed element" claim in place.
