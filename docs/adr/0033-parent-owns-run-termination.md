# The parent owns Run termination, and one predicate decides failure

> **Amended by [0044](./0044-native-runs-herdr-owns-the-process.md).** The principle below — the parent owns Run termination — is preserved deliberately. Its *mechanism* is not: every part of it (the errored-`message_end` reap, the 20-minute silent-stall watchdog, `runFailed`'s inputs) rests on the parent holding the child's pipes, and a **Native Run** is spawned by herdr so the parent holds none. Termination is observed from herdr's socket plus an exit-code sidecar, and stall detection moves to session-file staleness — which this ADR rejected as "indirect" on the express grounds that "the parent holds the child's pipes", the premise 0044 removes.

A **Run** ended only when its child process exited. `executeAttempt` parsed the child's `message_end` events and recorded `stopReason: "error"` faithfully, but nothing about an error settled the promise — only `close` did. A child that hit an unretryable provider error and stayed alive therefore left the promise pending forever: `Promise.all` never settled, `registry.finish()` was never reached, the **Task** stayed `running`, no **Reminder** fired, and one of six `MAX_ACTIVE_TASKS` slots was held for the life of the session. This happened twice in one evening on litellm 400s, both times leaving three oracle **Runs** reported as `running` more than 900 seconds after they were dead.

The parent now owns termination. An errored assistant message *is* the Run's outcome, so the child is reaped — SIGTERM, then SIGKILL after a short grace — rather than awaited. This is safe against cutting a recoverable attempt short because pi retries *inside* a turn and emits `message_end` only once it has given up: by the time the parent sees an errored message, the ladder is already spent. A second, wider net catches the silent case, where a child produces no error, no output and no exit at all: total silence for 20 minutes is treated as a stall, comfortably above pi's own worst-case ladder of about 10.6 minutes so a Run legitimately grinding through retries is never killed. Both paths converge on `close`, so the child is always reaped rather than abandoned, and both set `stopReason: "error"` rather than `"aborted"` — `aborted` remains the cancel path's word, so a wedged Run reports its true cause.

Separately, **failure had three hand-copied definitions** — one in `index.ts`, two in `tasks.ts` — which had drifted into agreement on the wrong thing: all three tested exit code and stop reason, none tested `errorMessage`. A child that reported an error and then exited cleanly was classified a *success*, surfacing as a completed Run with no output. There is now one exported `runFailed` in `tasks.ts` (beside `RunResult`, since `index.ts` imports `tasks.ts` and not the reverse) and an `errorMessage` fails a Run on its own.

**Considered.** *A fixed wall-clock deadline per Run* is the obvious hammer and was rejected because there is no defensible number: a legitimate oracle review ran 24 turns over ten minutes here, and any ceiling low enough to catch a wedge quickly would kill real work. Silence is the better signal, because a working child always streams. *Watching the Run's session file for staleness* would reuse what the **Board** already does, and was rejected as indirect: the parent holds the child's pipes, so it can see silence without touching the filesystem. *Parsing stderr for provider errors* was rejected because stderr is a diagnostic tail, not a control channel — the structured `message_end` stream already carries the outcome. *Treating any non-zero exit as the only failure signal* is what the code already did, and is precisely what let an exit-0 error pass as success. *Leaving the three predicates separate but adding `errorMessage` to each* was rejected as re-creating the drift that caused the bug.

**Consequences.** A Run can now be terminated by its parent, so `exitCode` no longer tells the whole story — a reaped Run exits 0 by SIGTERM while being a failure, which is exactly why `runFailed` cannot rest on exit code alone. The 20-minute stall threshold is a guess dressed as a constant: it is derived from the retry ladder, so if `maxRetries` or `maxDelayMs` rise, this must rise with them or long-retrying Runs will be killed as stalled. Making `errorMessage` fail a Run also forced a second change that was nearly missed: `errorMessage` used to latch, and since litellm 400s now retry, *surviving an error is the common case* — three oracle reviews errored three times each, recovered and delivered, and a latching error would have reported all three as failures. So a settled assistant message with no error now clears a stale one, making the Run's outcome its **last** message rather than the worst it ever saw. The identical latching bug still exists independently in the **Run Index** (`runindex.ts` sets `failed` on any errored message and never clears it), where it currently misreports those same three Runs, and wants the same fix. _[Since fixed: `scanLiveSession` now overwrites `failed` unconditionally per assistant message, so the Run Index is last-message-wins like the parent, and the error-retry Run named above scans as `completed`. Verified while implementing ADR 0044; this sentence is kept for the history rather than as a live defect.]_ Finally, this closes the hole under **Autonomous Mode**: a review that wedges now reaches a terminal state and reports it, which is what makes an unattended review loop safe to build at all.
