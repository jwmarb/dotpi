# The Run directory is a shared contract, not the Task registry

Autonomous oracle reviews spawned by the plan extension were invisible: no Mirror Pane, no `/runs` row, no Board progress. [ADR 0032](./0032-autonomous-mode-defaults-the-review-route.md) deferred fixing this and prescribed the remedy as "extract the Task registry into a shared module" so plan-spawned children become real registry Tasks. That prescription is wrong, and an oracle review of the architecture — commissioned before any code was written, precisely because the decision is expensive to reverse — agreed.

**Why the registry is the wrong unit.** The registry is in-memory *lifecycle* machinery: waiters, cancellation, admission control, drain. It is deliberately memory-only (ADR 0001). Extracting it would not deliver the one thing it would have been extracted *for* — the Reminder — because the Reminder lives in the subagent extension's host closure, bound to that extension's `agent_settled` handler, not in `tasks.ts`. The plan extension would still need its own completion channel, and it already has one: `dispatchReview` awaits its child. So the large unit does not buy the advertised benefit.

**What is actually needed is much smaller, because the three consumers are already disk-derived.** `/runs` (`scanRunDirs`), the Board's per-card progress (`readRunProgress`) and the Mirror Pane all read `<agentDir>/subagent-sessions/<runId>/` and hold no handle on the producing process. That is not an accident to be exploited but a documented design: the sidecar exists precisely so readers need no view of the Task (ADR 0026), and the reaper explicitly protects directories owned by *another* pi process via its freshness guard. A second producer was always anticipated.

So the plan extension becomes a first-class producer of that layout, and the layout itself is extracted into `subagent/rundir.ts`: directory paths, the sidecar writer, ID shortening, and the Mirror Pane label. Not the registry. The label is included specifically because it is also the `findPaneByLabel` de-duplication key — a second, separately-written copy would drift and silently open duplicate panes for one Run.

**The invariant a naive second producer would have dropped:** `run.json` is written **twice**. It starts `outcome: "running"` and is rewritten to `completed`/`failed` when the child ends, and the rewrite must happen in a `finally`, because a Run that threw or was killed is exactly the Run whose outcome a reader needs. The module therefore exposes `createRunDir` and `finalizeRunDir` — two functions named after the two moments — rather than one `writeSidecar` a caller could reasonably call once. Writing it once reintroduces the dishonest-waiting bug of ADR 0036 for a whole new class of process.

The second omission was blunter: `review.ts` passed no `--session-dir` at all. The child wrote its transcript nowhere discoverable, which is the entire reason reviews were invisible; stdout was being scraped for a Verdict and the transcript simply discarded. A `--mode text` child does write a readable `.jsonl` when given `--session-dir` — verified, since the whole direction depended on it and the docs do not promise it.

**Plan-spawned Runs use a `pln-` prefix.** The subagent extension reserves IDs found on disk with `/^(sub-[^-]+)-\d+$/`, so a distinct prefix keeps the two minting schemes independent with no shared counter, and makes the producer legible in `/runs`. `shortRunId` was generalised from the hard-coded `sub-` to any prefix, verified to return identical results on every real `sub-` ID so the extraction is behaviour-preserving.

**Fixing this exposed three honesty bugs in `/runs`**, all of the same family: it was deriving Run state from the session transcript while ignoring the parent's own record.

- Any truthy `stopReason` counted as finished, including `toolUse`, which means the *opposite* — the model paused to call a tool. This is the identical bug ADR 0031's Board fix addressed, still live in the other consumer.
- A Run mid-retry has `error` as its last stopReason but is alive and will likely recover. Since the retry patch (ADR 0034) made mid-Run errors routine, `/runs` was reporting healthy Runs as `failed` — observed live, with the registry and `/runs` disagreeing about the same Run.
- An *empty* Run directory was hardcoded to `running`, so a review that wedged and was killed before writing a transcript read `running` forever.

All three are fixed by treating `run.json`'s `outcome` as authoritative in **both** directions — the session and the parent are each blind where the other sees — and falling back to the transcript only for sidecars predating the field.

**Considered and rejected.** *Extracting the Task registry* (ADR 0032's literal prescription), for the reason above. *Treating the Reminder as load-bearing for safety*: the danger window for a rogue writer is *during* the run, and a notification afterwards does not touch it; the spawner already learns completion by awaiting its child. *Letting the plan extension re-implement the layout*, which is the drift this module exists to prevent. *Sharing a `sub-` ID space*, which would require a shared reservation mechanism across two processes to buy nothing.

**Consequences.** There is now a real cross-extension file dependency, plan → `subagent/rundir.ts`, mirroring the existing plan → `plan/board.ts` pane coupling; the alternative was duplicated layout knowledge, which is worse. `/runs` and the Board now list plan-spawned Runs alongside subagent Runs, so a reader must not assume every row came from a `subagent` tool call — the `pln-` prefix is how to tell. Anything parsing a Run ID by prefix must accept both. Finally, observability is **detection, not prevention**: it makes a read-only review accountable, and it is explicitly *not* sufficient to license an autonomous writer, which still needs an admission cap and a tool-scope or scratch-copy decision.
