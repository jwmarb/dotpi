# The Run Index groups by Task

`/runs` printed one row per **Run**. A parallel or chain **Task** therefore appeared two or three times, and every one of those rows carried the *same* **Task ID** — because a Run has no separately addressable identity in this system. `/run <id>` resolves a Task ID to *all* of that Task's Run directories and reopens them together, so three `sub-1ed9` rows were three ways to perform one action. Measured on disk: 18 rows for 13 Tasks, with 5 Tasks contributing 13 rows between them.

Runs are the unit of execution; the **Task** is the unit a human addresses. So the Task gets the row. A single-Run Task — the overwhelming majority — keeps exactly the old one-line shape, because indenting it beneath a header would be ceremony purchased with vertical space. A multi-Run Task gets a header carrying its ID, agent, aggregate state and *total* turns, followed by one indented child line per Run identified by its ordinal (`#1`, `#2`). The children are informational: they explain the header, and they are not separately actionable because nothing in the system can act on one Run alone.

**The header state is deliberately pessimistic.** It reads `failed` if any Run failed, else `running` if any is still going, and `completed` only when all are. Averaging or taking the majority would let a Task with one failed Run out of three read `completed`, hiding the single most important thing someone scanning this list wants to see. The same reasoning applies to `(archived)`: on a header it means every Run is archived, and a partially-archived Task is marked per Run rather than being flattened into a claim that is true of only some of it. A Task's timestamp is its *earliest* Run's, since that is when the Task began.

Two details are load-bearing and easy to get wrong. Ordinals are compared **numerically**, not as strings, or `sub-x-10` sorts before `sub-x-2` once a Task exceeds nine Runs. And column widths are computed across header rows **only** — including the indented children would pad every header by the indent width and leave a ragged gap down the listing.

**Considered.** *Collapsing to only the header* was rejected because the per-Run turn counts are the actual diagnostic value: `47 turns` across three Runs tells you far less than `9 / 14 / 24`, which shows one Run doing most of the work. *Making each Run separately openable* would be the alternative justification for one row per Run, but it means inventing a Run-level address (`sub-1ed9#2`) and threading it through `reopenTask`, the pane resolver and the Tab labels — real work for a capability nobody has wanted, and ADR 0016 already decided a Task's Runs are viewed together. *A `(3 runs)` suffix with no children* keeps one row per Task but throws away the counts. *Sorting Tasks by state so failures surface* was rejected because newest-first is the ordering people navigate by; a `failed` header is already conspicuous.

**Consequences.** `formatRunIndex` no longer emits one line per input entry, so its output line count is not the entry count — anything counting lines to count Runs is now wrong. The aggregate state is computed for display only and is not persisted anywhere, so it cannot drift from the per-Run truth in `run.json`. Both call sites (`/runs` and the orchestrator's `list` action) share the grouping, which is intended: an orchestrator reading a Task's Runs as one row matches how it delegated them. The `mixed` agent label is reachable only if a Task's Runs disagree about their agent, which a chain Task can legitimately do.
