# A rejected Item is reworked by a fresh Run

Autonomous Mode made oracle the reviewer of a Plan Item. A failing **Verdict** returned the Item to `active` with oracle's findings in its note — and then nothing happened. The loop stalled at exactly the point where work needed doing, which made the mode a reviewer rather than a worker.

Now a failing Verdict spawns a fresh `worker` Run whose only context is the Item's text and the findings. **The point is that it is not the agent whose work was rejected.** That agent moved the Item to `review`, which means it already believed the work was correct; asking it to re-judge its own approach is asking the wrong question. This session supplied the evidence rather than the theory: two of the bugs oracle caught — `board.ts` treating `toolUse` as finished, and `restoreScreen` never leaving raw mode — were written *and declared verified* by the orchestrator, then failed review. A fresh Run reads the findings without having authored the thing they criticise.

This is the only place in the system where a machine's judgement makes a machine modify the repository with no human in the loop, so it waited on four properties, all of which had to be built first. The Run is **observable** — a `pln-` Run directory with a `/runs` row, Board progress and a Mirror Pane ([0039](./0039-run-directory-is-a-shared-contract.md)). It is **bounded** — it claims a slot from the one shared cap of six ([0040](./0040-one-spawn-cap-for-every-child.md)). It is **revertable** — the repo is now under git, which replaced the scratch-copy discipline 0039 asked for; a `cp -r` sandbox buys nothing that a revertable commit does not. And it is **finite** — the **Review Budget** bounds the loop, and a Rework is dispatched only on a Verdict that did not exhaust it, so at most one worker runs per Item before the route ratchets to `user`.

**The worker keeps `bash`.** Workers have it by default, and a worker that cannot run a build or a test cannot verify its own fix — it would produce exactly the unverified edit that got rejected. Its prompt therefore tells it to run the thing it changed, and to commit **one** commit, because an autonomous edit that is not a commit is an unattributable change in the working tree and one commit per Rework is what makes a bad one revertable on its own. It is also told it may push back: if the findings are wrong, saying so and changing nothing is a better outcome than forcing a fix it cannot defend.

**One spawner, two purposes.** `runReview` takes a `purpose` and spawns either child. A writer and a reader are different risks, so a separate spawner is tempting — and rejected, because everything dangerous is shared: proving the spawn target is really pi, the doubled recursion interlock enforced *at the spawner* rather than trusted to callers, the synchronous slot claim, the non-empty plan-key sentinel. Every one of those was a bug once ([0037](./0037-spawning-pi-requires-proving-the-target.md), 0040), and a second copy of that function is precisely how the first interlock was bypassed. What is *not* shared is policy: a Rework gets forty minutes rather than twenty-five (a real worker Run in this repo's own history took 15.3 minutes, uncomfortably close to a reviewer's deadline and without running a test suite), and a thirty-second SIGTERM grace rather than two, because SIGKILL during `git commit` can leave `.git/index.lock` and a half-staged index — turning "exactly one commit" into no commit plus a dirty tree that nothing describes.

**The loop deliberately stops after one Rework.** Nothing moves the Item back to `review`; a human or the orchestrator re-submits it. Auto-advancing would close the loop, and the Review Budget already bounds it to two Verdicts and one worker, so it is not a runaway risk — it was rejected for two other reasons. The second oracle is not independent evidence: it is the same model reading the first oracle's findings plus a rework report, which is confirmation rather than a second opinion. And a closed loop pays [0032](./0032-autonomous-mode-defaults-the-review-route.md)'s unattended-clear cost twice over. Stopping also buys the evidence to decide later: if Rework-then-resubmit passes almost every time, the loop is closed in practice and auto-advance is a one-line change; if it usually fails, auto-advance is pure spend.

**A re-review must not judge code a worker is still changing.** An oracle review commissioned for this decision found a race, and running it confirmed the bug rather than merely predicting it: the Item sits in `active` while the worker runs for minutes, the `status` op re-dispatched a review unconditionally, and a stale `fail` about pre-fix code spent the last Budget unit and ratcheted the route to `user` — which the ratchet makes **irreversible**, permanently demoting an Item the worker had in fact fixed. So an Item now carries `reworkRunId` while a Rework is in flight, and a review refuses to start against it. The marker lives on the Item, not in the Run sidecar, because `run.json` records the Run but not which Item it serves and so cannot answer "is anyone reworking p1?". Crucially, the *Run's own recorded outcome* decides, not the marker's presence: a marker orphaned by a killed host reads as "not running", so an interlock can never become a permanent stall.

**Considered and rejected.** *Auto-advancing to `review`* (above). *A separate spawner for the writer* (above). *A hard lock on "who owns this Item"* — the plan lock serialises writes to the file, not work on the repo, and a full ownership lock is over-engineering for one cooperative host; the in-flight marker closes the case that actually bites. *Replacing the note with the worker's report* — oracle's findings are why the Rework happened and must survive it, or the next reader sees a fix with no statement of what it was fixing; appending is safe only because at most one Rework precedes escalation, so no worker ever reads a previous worker's report. **If `REVIEW_BUDGET` is ever raised above 2, that stops being true** and the appended lines need a supersede-not-accumulate convention, since a second worker would otherwise read `findings1 + rework1 + findings2` as though all of it were the reviewer's findings.

**Consequences.** A Plan Item gained a field that means "a process is editing this right now", which is the first piece of state in the plan file about something happening *outside* the plan. Two writers on one repo remain possible in principle — the orchestrator may work an Item while a worker does — and the mitigation is git plus the worker's instruction not to commit unrelated dirty files, which is prompt-level discipline on a small model, not a mechanism. The `status` op still has no in-flight dedup, so a double-submit burns two of six shared slots and two oracle runs; the in-lock re-check prevents state damage, not cost. And a Rework worker's edits are verified by the worker itself and then by oracle, never necessarily by a human before the Item clears — which is what Autonomous Mode is, stated plainly.
