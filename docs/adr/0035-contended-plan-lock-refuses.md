# A contended plan lock refuses the write, and collected Tasks close their own Tabs

Three related defects, all of the same shape: a guard that existed but did not cover the path that mattered.

**The plan lock gave up and proceeded unlocked.** After a three-second wait, `acquirePlanLock` returned a no-op release function and let the mutation run anyway. The reasoning written into the code was that the in-process mutation queue and the atomic rename bound the damage — but the queue only serialises writers *inside one process*, and the contending writer is another process: every subagent child loads this same extension with its own `PI_PLAN_KEY`, and ADR 0015 grants the Board write access too. Two processes could each read, mutate and atomically rename, and the second rename silently discarded the first writer's item. **Atomic rename prevents a torn file, never a lost update.** The lock now throws `PlanLockTimeoutError` instead: a refused mutation is visible and retryable, a lost one is neither. pi already converts a thrown tool error into an `isError` result carrying the message, so the refusal reaches the agent as actionable text with no wrapper needed.

**A stale-broken holder could delete its replacement's lock.** Breaking a lock judged stale created a new one with no way to tell the two apart, so the original holder — slow, not dead — could return from its write and remove the *new* holder's lock, leaving two writers running unlocked. Each acquisition now carries a token recorded in `owner.json`, and `release` removes the lock only while that token still matches. Breaking a stale lock is a separate operation that deliberately ignores ownership, so an abandoned lock is still breakable and the fix does not trade a lost update for a deadlock.

**`attach` validated one snapshot and mutated another.** It called `attachTaskId` on a freshly loaded list, then called `mutatePlan`, which re-reads the file under the lock and assigned `taskId` directly without re-running the guards. An item could therefore go terminal between the two reads and still be modified, and the reported "replaced the earlier X" could describe the stale snapshot rather than what was actually overwritten. Validation now happens *inside* the `mutatePlan` callback, on the same list being written.

**Separately, collecting a Task's Results leaked its Tab.** ADR 0028 closes a Task's Tab when its **Reminder** is delivered. But `subagent_tasks` `wait` and `result` both claim `notified = true` to suppress the duplicate Reminder — which meant the only thing that closed a Tab never ran. The Tab leaked precisely on the orchestrator's normal path, so the feature appeared to work while doing nothing in the common case. All three collection points now close the Tabs they report on. `closeTaskTab` also claims `task.tabId` *before* awaiting rather than after, because it is now reachable from five places that can overlap within one turn; verified at one `closeTab` call under three concurrent callers, where the old ordering fired three times.

**Considered.** For the lock: *breaking a live lock instead of refusing* loses the holder's write outright, which is the same silent data loss from the other direction. *Waiting indefinitely* converts a lost update into a hang on the user's own plan file, and the ADR 0015 reasoning that an unbreakable lock is worse than the race still stands. *A longer wait budget* only narrows the window; the failure is structural, not slow. *Making the write idempotent instead of locked* does not help, since the lost update is a whole-file rename, not a conflicting field. For the Tab leak: *closing the Tab when the last Run finishes* is what ADR 0028 explicitly rejected — the Tab would vanish before the user is told anything. *Not claiming `notified` in `wait`* would restore the duplicate Reminder that ADR 0027 exists to prevent. *Closing Tabs on a timer* was rejected as a guess about when the user stopped looking.

**Consequences.** A plan mutation can now fail, which it never could before: any caller that assumed `mutatePlan` always succeeds is now wrong, and the honest failure mode under **Autonomous Mode** — where far more concurrent writers exist — is a refused attach that must be retried rather than a plan item that quietly vanishes. The ownership token makes `owner.json` load-bearing rather than a debugging aid, though a missing or token-less owner file is still treated as breakable so older locks and older builds keep working. Closing Tabs from four places means the close is best-effort in four places; a failed close is deliberately not retried, since a Tab that refuses to close is herdr's problem and not the Task's. Finally, `attach` now reports refusals discovered under the lock, so the same call can succeed or be refused depending on what another writer did in the meantime — correct, but it means the message, not the call, is the source of truth about what happened.
