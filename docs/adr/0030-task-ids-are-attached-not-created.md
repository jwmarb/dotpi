# A Task ID is attached to an existing Plan Item, not set when the Item is created

**Attaching** a **Task ID** to a **Plan Item** is its own operation (`plan` op `attach`), separate from creating the Item. Previously the only way to record one was at creation, which was unusable for the case it existed to serve: an Item is always groomed and started *before* the delegation that executes it, so at `add` time there is no Task ID to record. The tool's own guidance told the orchestrator to "record the Task ID on the plan item that delegates the step", and no operation could do it.

Worse, the creation path did not work either. The `add` handler read `params.taskId`, but `PlanParams` declared no top-level `taskId` — the field existed only inside the per-item schema used by `seed`. So `params.taskId` was always `undefined`, and `seed` was in practice the sole way any Item ever acquired a Task ID. That is why ADR 0026's **Board** progression looked broken in normal use: cards render live progress only when they carry a Task ID, and outside a seeded **Starter Plan** no card ever did. Adding the missing parameter fixes `add` as a side effect, but `attach` is the operation that matters, because it is the one that matches when the information actually arrives.

`attach` refuses a terminal Item for the same reason `revise` does — a terminal Item is a record of what happened (ADR 0014) — and refuses an unknown id. Re-attaching a *different* Task ID is allowed and reported rather than silently overwritten, because a step re-delegated after a failure is a real case and quietly losing the previous ID would hide it. It is not a status change, so it does not trigger the self-archive check and does not touch Item order or status.

**Considered.** *Extending `status` with an optional `taskId`* binds recording a delegation to a state change, so escalating an already-`active` Item would need a redundant transition. *Extending `revise`* was rejected because `revise` rewrites text and explicitly preserves `taskId` — overloading it would blur two different edits. *Having the `subagent` tool write the Item itself* removes the orchestrator's step entirely and was rejected as cross-extension coupling: the subagent extension would have to know the plan file format and take its lock (ADR 0015). *Deriving the link by convention* — matching a Task's **Starter Plan** key back to the parent Item — needs no new op at all, and fails because the key names the child's plan, not the parent's Item.

**Consequences.** The orchestrator now has a two-step protocol for delegation: create the Item, delegate, then attach. Nothing enforces the third step, so a forgotten `attach` shows up only as a Board card with no progress line — the same silent failure as before, just now avoidable. `taskId` becoming a real top-level parameter means `add` accepts it too, which is redundant with `attach` but harmless and occasionally convenient for an Item created after its delegation. Note the verification trap this change sat in: the repo has no `tsconfig`, so `bun build` transpiles without type-checking, and a malformed schema — `taskId` nested inside the `state` property rather than beside it — bundled cleanly while being wrong. Structural inspection of `PlanParams`, not the build, is what caught it.
