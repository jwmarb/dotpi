# A Run is a native pi session in a pane; the premise that forbade it was false

Supersedes the ownership model of [0016](./0016-mirror-pane-displays-never-owns-the-run.md) and, with it, the reasoning of [0019](./0019-runs-get-real-session-files.md), [0020](./0020-mirror-pane-renders-session-file-no-pty.md) and [0021](./0021-mirror-pane-claims-official-pi-identity.md). A **Run** is no longer a JSON-mode child whose output a **Mirror Pane** re-renders. It is a real interactive `pi` TUI launched by herdr into its own pane: the user watches it, types into it, and steers it exactly as they steer the orchestrator.

**The decision was reversed because its stated reason was measurably false, not because the trade-off was re-weighed.** Three ADRs rejected "letting herdr own the run" with one sentence between them: *the Result would then have to be scraped from a terminal.* That was true of the mechanism available when 0016 was written, and it is not true of the mechanism that exists now. `modem-dev/pi-herdr-subagents` — a public, working extension solving this exact problem against herdr and pi — scrapes no terminals. The child loads a small extension with `-e` which exposes a `subagent_done` tool; the tool writes a `<session>.exit` sidecar and calls `ctx.shutdown()`. The **Result** is then read from the child's own session JSONL, which [0019](./0019-runs-get-real-session-files.md) already causes to be written and [0020](./0020-mirror-pane-renders-session-file-no-pty.md) already causes to be parsed. The transport that was assumed impossible was in fact already half-built here for a different reason. A rejection repeated three times acquired the authority of a principle while resting on a fact nobody re-checked; the lesson is that a *reason* recorded in an ADR has a shelf life, and repetition is not re-verification.

**What actually forced work is the loss of the pipes, which no one had costed.** `pi` resolves to TUI mode only when stdin *and* stdout are both TTYs. A child spawned by `node:child_process` with `stdio: ["ignore","pipe","pipe"]` therefore cannot be a TUI, and no flag changes that: herdr must spawn the process, which means the parent no longer holds its pipes. Everything [0033](./0033-parent-owns-run-termination.md) built stood on those pipes — the errored-`message_end` reap, the 20-minute silent-stall watchdog, and the `message_end` stream `runFailed` reads. `pane.exited` carries no exit code (verified against herdr 0.9.0's own API schema: `exit_code` appears only under `PluginCommandLogInfo`). So 0033's *principle* survives — the parent owns termination — while its entire mechanism is replaced: the parent subscribes to herdr's socket (`pane.exited`, `pane.closed`, `pane.agent_status_changed`) and reads a wrapper-written `.exitcode` sidecar for the code herdr does not report.

**Stall detection moves to session-file staleness, which 0033 explicitly rejected — correctly, at the time.** 0033 declined to watch the session file because *"the parent holds the child's pipes, so it can see silence without touching the filesystem."* That premise is precisely what this change removes. When the justification for a rejection is deleted, the rejection goes with it, and the **Board** already reads exactly this signal.

**The launch must not go through a shell.** `herdr pane split --env` followed by `pane run` is available and is what the Mirror Pane does today, but it types a command into an interactive shell, and upstream reproduced the resulting race 100% of the time — shell init (direnv, devenv) swallows the typed command, with a swallow threshold of roughly 0.5–1s *even warm*. A race that loses a mirror is cosmetic; a race that loses a Run is not. So a Run is launched through a herdr **plugin pane** with an argv entrypoint: a static dispatcher `exec`s a generated wrapper script named by an environment variable, under non-interactive bash. There is no typing, no delay and no readiness probe, because there is nothing to verify. This is new install surface — a `herdr-plugin/` directory in this repo and a `herdr plugin link` step, where today no herdr plugins are installed at all — and that setup cost is the price of deleting a whole class of failure.

**Two glossary guarantees invert, and both were flagged as ambiguities precisely because they were load-bearing.** Closing a pane used to mean *you stopped watching*; now the pane is the process's home, so closing it ends the **Run** — and that is a *distinct* outcome, neither `completed` nor `failed`, because a Run the user dismissed is not a Run that went wrong. And **Reopen** retires as a word: the user chose that revisiting a finished Run means resuming a real `pi` on its session file, which appends turns to it. [0021](./0021-mirror-pane-claims-official-pi-identity.md) measured that append and treated it as corruption; it is now the intended behaviour, so a Run's transcript is a living document rather than a record. There is deliberately **no** read-only path: `pi --export` to HTML was offered and declined. The cost is accepted knowingly — every revisit of a Run can alter its transcript, and there is no way to merely look.

**Nesting breaks the spawn cap, and [0040](./0040-one-spawn-cap-for-every-child.md) predicted this in its own last sentence:** *"The cap is per-process and dies with the orchestrator, which is correct while children cannot spawn and wrong the moment they can."* A native child is a full `pi` with the subagent extension loaded and its own module-level counter, so six becomes six *per process*, recursively. Nested Runs get native panes anyway — consistency was preferred to a special case — which makes `spawnlimit.ts` cross-process work, in the shape [0035](./0035-contended-plan-lock-refuses.md) already uses for the plan lock.

**Considered.** *Installing `pi-herdr-subagents` as-is* is by far the least work and was rejected because it is a parallel system: its own `subagent` tool colliding with ours (pi resolves duplicates first-loaded-wins), and no concept of **Task**/**Run**/**Mode**, the **Board**, the **Run Index**, **Plan Items**, spawn slots or **Reminders** — the 5,300 lines those cost would go dark to buy a nicer pane. *Adopting it and bridging its events into our registry* was rejected for depending on another repo's internal contracts, which it explicitly calls a cross-extension contract down to sidecar key order. *Building from herdr primitives while ignoring upstream* was rejected as an invitation to re-derive the launch race and the dishonest-lifecycle bug it documents. *A better renderer instead of a native session* was put to the user directly as the cheap path — it delivers pi-fidelity output with every ADR intact and roughly a `mirror.ts` rewrite — and was rejected because the actual requirement is intervention, which a renderer cannot give. *Read-only-then-takeover* was rejected: the pane is a real PTY, so "read-only" would be a fiction herdr cannot enforce. *`herdr agent start --kind pi`* is purpose-built and validates readiness, but on herdr 0.9.0 accepts only `--kind --pane --timeout` — no `--env`, so it cannot carry `PI_PLAN_KEY`. *Flagging a steered Run's Result as human-influenced* was declined: a Run is a Run, and the transcript records the truth.

**Consequences.** The **Mirror Pane** concept dies for live Runs and, with `Reopen` retired, has no remaining consumer; `mirror.ts` (~490 lines) and the [0021](./0021-mirror-pane-claims-official-pi-identity.md) compatibility shim — the reserved `herdr:pi` source claimed with `HERDR_AGENT=pi`, which 0021 warned "a herdr upgrade may tighten and break" — both become deletable, since a native child self-reports through the installed `herdr-agent-state.ts` for free. That extension's `ctx.mode !== "tui"` gate, which today silently excludes every Run, becomes the mechanism instead of an obstacle. The JSON path cannot be deleted: it remains the automatic fallback whenever herdr is absent (headless, CI, `--mode json`), so **two spawn paths exist indefinitely** and may drift — the same maintenance burden 0021 accepted for its fallback, now permanent and larger. A **Run**'s outcome gains a fourth value for user dismissal, which the **Board**, **Run Index** and `run.json` must all learn. The `<result>` contract stops being load-bearing: `subagent_done` (auto-injected into every native Run's allowlist, so the 7 agent definitions need no edit) plus auto-done on a clean `agent_end` supply the signal, and the last assistant message supplies the payload. Most importantly, **a Result is no longer necessarily the subagent's own work** — the user may have typed it — and the orchestrator consumes it identically either way, including when a `chain` feeds it to the next Run. Nothing marks the difference, by choice.

## Verified mechanism (spike, herdr 0.9.0, 2026-09-13)

Everything above was decided against a *read* of herdr's API schema and of the reference implementation. A spike then ran it. The architecture is confirmed on every load-bearing point — a plugin pane launches an arbitrary argv process into a real PTY (`/dev/pts/6`, stdin/stdout/stderr all TTYs), `--env` reaches the child verbatim, a real interactive `pi` came up in the pane, and herdr **detected it as a pi agent with a non-null `agent_session`** through the already-installed `herdr-agent-state.ts`, with no `HERDR_AGENT=pi` shim and no `-e` flag. The ADR-0021 payoff is real.

Four findings change the *implementation*, and are recorded because each one would otherwise be discovered as a bug:

1. **Herdr auto-closes the pane the moment the process exits**, for clean and failing exits alike, and the pane then vanishes from `pane list` — `pane read` returns `pane_not_found`, so **scrollback dies with the process**. "Hold the pane open on failure" (decision 6) therefore cannot be asked of herdr: the *wrapper* must hold itself open on a non-zero exit, which is exactly what the reference's `read -r` guard does. That guard is not a nicety, it is the only thing standing between a failure and the total loss of its evidence.
2. **`pane_closed` does not fire on an exit-triggered close** — only `pane_exited` does. `pane_closed` fires only on an explicit close. This is *fortunate*, because it makes **Dismissed** cleanly detectable rather than inferential; but it also means a watcher gating on `pane_closed` would deadlock on every normal Run.
3. **No exit code is available anywhere**, confirming the schema reading and then going further: `plugin log list` stayed empty even after a deliberate exit 42, so `PluginCommandLogInfo.exit_code` never materialises for plugin panes. The wrapper-written `.exitcode` sidecar is the *only* source, and combined with finding 1 the wrapper is load-bearing twice over.
4. **An entrypoint is a static `[[panes]].id` in the manifest bound to a fixed `command` argv, and `plugin.pane.open` has no command-override field.** Per-Run variation *must* ride on `--env`. Verified both ways: a direct-argv entrypoint ran without any shell indirection, and one entrypoint launched three different processes purely by varying `PI_HERDR_LAUNCH_SCRIPT`. So the static-dispatcher indirection is *required* for per-Run variation, not stylistic.

Two smaller traps: the session file is written **lazily**, so herdr reports an `agent_session` path that does not yet exist on disk — anything waiting on that file must tolerate its absence (as ADR 0036 already found from the other direction). And a `pane.agent_status_changed` subscription is rejected without a `pane_id`, though the schema marks only `subscriptions` as required: schema and server diverge, and the server wins.

The launched child inherits the herdr **server's** environment, not the requesting pane's — so every variable a Run needs (`PI_PLAN_KEY` included) must be passed explicitly through `--env`. Nothing is inherited from the orchestrator by accident, which incidentally makes the nesting-env question (ADR 0044, nesting) an explicit choice rather than a leak.

## Three defects the first real Run exposed

The design above survived contact with reality; three implementation assumptions did not. Each was invisible to review and obvious the moment a native Run actually ran, so each is recorded here rather than left as a silent fix.

**`pi` is not necessarily one word — and `argv[1]` does not survive the trip.** The launcher passed `getPiInvocation().command` as "the pi binary", but that helper returns a *runtime plus a script path* whenever pi runs as a bundled script — so the wrapper executed bare `node` with pi's own flags and died with `bad option: --session-dir`, exit 9. Passing the whole prefix fixed the symptom and left a deeper fault: `getPiInvocation` exists to re-invoke *this* process, and reaches for `process.argv[1]`, which is meaningless inside a shell script herdr runs later in a different process. A separate `nativePiCommand` now resolves pi for the child specifically — `PI_BIN`, else an executable `pi` on `PATH`, else this runtime plus its entry script. The `PATH` case is preferred precisely because the installed launcher carries its own `#!/usr/bin/env node` shebang, so it is one word that cannot be split from its script. **The general lesson: a command that will be executed by another process later must be resolved absolutely, not derived from the current process's argv.** The failure was *legible* only because the pane held itself open, which is the first practical vindication of that decision: the same fault under the old auto-closing behaviour would have left an empty run directory and no explanation.

**A held-open pane must not hold a Spawn slot.** The wrapper deliberately stays alive on failure so the error stays on screen, which means the process outlives the work by up to an hour. The watcher originally settled only when the pane died, so one visible failure would have held a slot for that whole hour and six of them would have starved the tree-wide budget the same ADR just built. The watcher now settles as soon as the `.exitcode` sidecar appears: **the exit code is the Run being over, and the pane outliving it is presentation, not work.** This separation only exists because failure-holding does.

**The child's answer is not always its last words.** A child answered "Jupiter is the largest planet in the solar system" *in the same turn* as its `subagent_done` call, and pi then emitted a courtesy turn reading "Done." once the tool returned. Reading the transcript's last non-empty assistant text therefore reported `"Done."` as the **Result** — a perfectly-formed, entirely useless answer. The turn that calls the done tool is now authoritative: the child declared itself finished there, so what it said then is its answer and anything after is epilogue. Note what this means in general — retiring the `<result>` tag moved the ambiguity rather than removing it. The tag said "this is the answer" explicitly; the transcript requires *inferring* it, and the done-tool call is the only reliable marker of where to look.

A fourth, smaller one surfaced the first time a Native Run completed through the real `subagent` tool rather than a test harness: the Result arrived correctly and was **prefixed with a warning scolding the subagent for not using `<result>` tags**. The contract was retired for this path by this very ADR, so the check was admonishing a child for obeying its own design. Both result-formatting sites now skip it for a Native Run. Worth recording because the bug is a *category*: retiring a contract means finding everything that still enforces it, and an enforcement point is easy to miss precisely because it lives with the readers rather than the writers.

## Nesting, and the grant ADR 0040 told us to guard

Nesting is on: a **Native Run**'s allowlist now carries `subagent` and `subagent_tasks`, so a child can delegate in turn. This is precisely the capability [0040](./0040-one-spawn-cap-for-every-child.md) singled out — *"If an agent is ever given one of those tools, this stops being true and the cap must become cross-process… That grant is the thing to guard"* — so it was switched on last, after the guard was in place and measured, rather than as part of the same change.

**What makes it safe is one property, and it was verified before the grant.** A separate process was made to hold five slots; a second process then saw all five, took the sixth, and was refused the seventh with a message naming the holders. Six means six across the whole descent, not six per process. The measurement matters more than the mechanism: a per-process counter would have made nesting mean six, then thirty-six, then unbounded, and nothing in the code would have looked wrong.

Two smaller properties were confirmed alongside it, because both are ways the cap could fail *open* rather than closed. Tokens are reaped by probing the holder's pid, so six tokens left by a killed process were collected by the next process to look and the count returned to zero — a crash cannot permanently consume the budget. And liveness is never inferred from age, because a **Native Run** may legitimately hold a slot for hours while a user steers it; an age-based rule would reap live holders, which is the failure that over-admits.

A real two-level delegation was then run end to end: a parent Run spawned a nested Run, waited on it, and relayed its answer. Both levels were genuine `pi` TUIs in their own panes — the nested Run has its own wrapper and **Done signal** sidecar on disk, so it was native too, spawned by a child rather than by the orchestrator. Both slots were released on completion.

**Consequences.** The grant is recorded as a named constant (`NESTING_TOOLS`) rather than inlined, so it is greppable and so the next reader meets the dependency instead of inheriting it: if the **Spawn slot** budget is ever narrowed back to one process, these tools must be withdrawn in the same change or the tree becomes unbounded. Note also what nesting costs that the old JSON path did not: each level is a full interactive `pi` with its own context window and its own pane, so a deep delegation is expensive in a way a piped child was not — the cap bounds the damage, it does not make it cheap.

A fifth appeared once **Dismissed** was exercised through the real tool rather than a synthetic pane: the Task correctly reported *"the user closed the Run Pane before the Run reported completion"*, and then **stranded an empty Tab**. A dismissed Run counts as failed for the narrow purpose of "did this produce a Result?", so it took the hold-the-Tab-open branch — but a dismissal has nothing to read. The user closed that pane themselves and herdr had already destroyed it, so the branch preserved evidence that did not exist and left a bare shell to be closed by hand. The hold now requires a *readable* failure. The distinction is the one this ADR drew in the first place, applied one level further down: dismissal and failure share a destination but not a meaning, and anywhere the code treats them as one thing is a place to check whether the meaning still fits.

## Autonomous reviews are native too, reversing this ADR's own assumption

This ADR originally scoped reviews out: the native path covered delegated `sub-` Runs, and `plan/review.ts` kept spawning its own `--mode text -p` child. That was recorded as an assumption and never revisited, and the consequence was the exact failure this whole change set out to remove — **an autonomous review left no pane and no tab, so the one Run type that runs *without a human* was the one a human could not watch.** It surfaced the way such things do: two reviews were dispatched, both reported real findings, and the user asked why nothing had appeared on screen.

Reviews now take the same native path. Three things had to be settled to get there, and each is a decision rather than a detail.

**The Verdict comes from the transcript.** It was parsed from accumulated stdout, which a TUI does not have. [0037](./0037-spawning-pi-requires-proving-the-target.md) made that contract deliberately strict — the token must be the last non-empty line, with no prose fallback, because "guessing a conclusion gets read as one" — but that strictness is about *parsing*, not about the channel, so it survives the move intact. The native path fills the same `output` field, `parseVerdict` applies the same rule, and a missing token is still a **Dead review** rather than a guess. The result is *better* than before: stdout carried startup noise (`[mcp] 1/1 server(s) connected…`) into the text being parsed, while the transcript carries only what the model said.

**A steered review is still a review.** The user chose consistency with every other **Native Run**: you can type into a review's pane, and the transcript records it. This is a sharper version of the ambiguity already flagged for Results — a verdict you influenced can clear your own work — and it is accepted knowingly rather than by omission. Autonomous Mode's promise is that a review runs *without* you, not that it is sealed against you.

**A review may not delegate.** `buildSubagentToolAllowlist` injects `subagent`/`subagent_tasks` for nesting, and handing those to a review would route straight around 0037's recursion interlock into a different spawner — the interlock stops an autonomous child dispatching *reviews*, not subagents. So the allowlist takes an `allowNesting` flag, false for reviews and reworks. A reviewer also simply has no business delegating: its verdict is meant to be its own reading of the work.

Two smaller consequences worth naming. A review's pane closes on **both** outcomes, unlike a delegated Run whose failure pane is held open — a review's findings are recorded on the **Plan Item**, so there is nothing on screen worth preserving, whereas a failed Run's pane holds the only diagnosis of it. And the recursion interlock now has to travel in the *pane's* env, because a herdr-launched process inherits the herdr server's environment rather than the spawner's; missing that would have quietly disarmed the guard that prevents a review-spawning-reviews fork bomb.

**A sixth defect, found by the first native review.** It silently fell back to the piped path, and the tell was startup noise in the parsed output plus a missing `.exit` sidecar. Cause: the pane request passed `placement: "tab"` *and* a `direction`. A Tab has no pane to split from, so herdr rejects the combination outright rather than ignoring the surplus field — and because `openPluginPane` returns null on any failure, the rejection was indistinguishable from "no herdr" and took the fallback. Fixed at the call site and then again at the source: the socket client now drops `direction` unless the placement is a split, so no future caller can reproduce it. This is the third bug in this series whose shape is *a legal-looking combination that one layer accepts and the next rejects*, and the second where a silent fallback hid it.
