# Reminders are delivered on idle, because a queued followUp cannot be recalled

A **Reminder** is no longer sent when a **Task** finishes. It is sent when the orchestrator next goes idle (`agent_settled`), and any Task whose **Result** was collected in the meantime is dropped by the existing `notified` guard.

The cause is a delivery semantic, not a missing guard. `pi.sendMessage(..., { deliverAs: "followUp" })` is *queued* when the agent is mid-turn — the framework delivers it "only when agent stops" — and there is no unsend. So the previous eager delivery on completion created an unwinnable race: a Task that lands mid-turn has its Reminder queued immediately, and if the orchestrator then collects that Task itself with `subagent_tasks` `wait` in the same turn, the queued copy still surfaces after the turn ends, re-injecting Results the orchestrator has already read. The `wait` path's claim-before-await (marking `notified` before blocking) cannot help, because the send has already happened.

Two cases keep their old behaviour deliberately. A Task landing while the orchestrator is *already idle* is delivered immediately, since no further `agent_settled` is coming and waiting for one would strand it forever. Headless has no settle event at all, so it still delivers inline — consistent with ADR 0005, where a headless Task is drained during the turn and its Reminder suppressed up front.

**Considered.** *Revoking the queued message* is the obvious fix and is impossible: `sendMessage` returns nothing and the extension API has no unsend. *`deliverAs: "nextTurn"`* was rejected because it changes when a Reminder appears without changing whether a collected Task still sends one — the duplicate survives. *Suppressing the Reminder inside `wait` by comparing content* would need to reach into the queue it cannot see. *Accepting the duplicate* was the status quo: it breaks nothing, but every duplicate re-injects a full **Write-up**, and in a session with many delegations that is a large amount of context spent restating what the orchestrator just read.

**Consequences.** Reminder delivery is now coupled to turn lifecycle events, so the extension tracks whether a turn is in flight — a small amount of state that must stay correct or Reminders stall. If `agent_settled` were ever not to fire after a turn, a Task landing mid-turn would sit unannounced until the next settle; the idle-path immediate delivery limits but does not eliminate that exposure. The upside beyond deduplication is that a Reminder now never interrupts a turn in progress, which is what ADR 0006 wanted when it made Reminders system-attributed rather than simulated user messages. Note the debugging trap this bug set: because the extension is loaded once at session start, an edit to it cannot be exercised or instrumented until `pi` restarts, and instrumentation added mid-session records nothing — which initially looked like evidence that the delivery path was never called at all.
