# Autonomous Mode defaults the Review Route, and a fresh Run does the Rework

> **Status: implemented.** Its dependency
> [0023](./0023-review-routes-per-plan-item.md) is built, and so is the whole
> loop: the `plan-meta` line, the `autonomous` op, the `oracle` default, the Board
> banner, the strict `parseVerdict`, `applyVerdict` with the
> **Review Budget** ratchet, and the dispatcher in `review.ts` that spawns oracle
> as a detached `pi` subprocess when an `oracle`-routed Item enters `review`.
>
> **Two claims in the body below are stale.** `Rework` *is* now delegated to a
> fresh Run ([0041](./0041-rework-is-done-by-a-fresh-run.md)), and this repo *is*
> under version control. The `oracle` default also did nothing at all in practice
> until the gate was moved off `ready`. All three are corrected in the final
> amendment — read it before acting on anything above it.

**Autonomous Mode** is a per-plan setting that changes exactly one thing: a **Plan Item** **Groomed** while it is on defaults to the `oracle` **Review Route** instead of `user`. An Item explicitly routed `user` still waits for the user's hand. When an `oracle`-routed Item enters `review`, a review is dispatched without being asked for; its **Verdict** decides what happens next. `pass` clears the Item. `fail` and `unsure` both return it to `active` for **Rework** — the Item keeps its text and gains oracle's findings in its note. A **Rework** is carried out by a *fresh* **Run**, never by the orchestrator whose work was rejected. After the **Review Budget** is spent the Item's route ratchets to `user`, so a problem oracle keeps rejecting reaches a human instead of consuming runs forever. The budget was **two** when this ADR was written and is now **twenty**: two rounds proved too eager, because an Item can be genuinely improved by each **Rework** and still be rejected twice on different grounds, which parked correct-and-improving work in front of a user with nothing to add. The ratchet is now a runaway stop rather than a routine handoff — the termination guarantee is unchanged, only the ceiling moved.

The mode is stored as a **plan-meta line** — a single JSON object carrying `kind: "plan-meta"` at the head of the plan file, beside the one-per-line Items. The plan file was pure item JSONL, so a per-plan field had nowhere to live, and the obvious cheap move — just writing an extra line — is a trap worth recording: both parsers *tolerate* an unknown line (they require `id`, `text` and `status` to be strings), so the mode reads back correctly and looks fine, but every writer rebuilds the whole file from the item list alone, so **the first mutation after setting the mode silently deletes it**. This was confirmed by experiment before the fix, not reasoned about afterwards. Meta is therefore read and rewritten inside the same lock as the items, and `loadPlan` skips the meta line explicitly rather than relying on it lacking item fields — so adding a field to meta later can never make it parse as an Item.

One consequence of the split between the mode and the dispatcher is worth naming, because it is a privilege boundary. `applyVerdict` sets `done` *directly*, bypassing the route guard in the `status` op. That is correct — a `pass` **is** the `oracle` route being satisfied — but it means the function is the one place in the extension that can clear an Item without the user, so it must only ever be called with a Verdict from a real review of an `oracle`-routed Item. Anything that let agent- or user-supplied text reach it would turn it into a way to set `done` on work the user was meant to clear.

Building the dispatcher exposed a hazard the design had not accounted for: **a review child loads this same plan extension**. Nothing distinguishes it from any other `pi` process, so it has a plan tool, it can groom Items, and it would dispatch reviews of its own — unbounded recursion at roughly ten minutes and one oracle-grade model call per level. The interlock is an environment flag, `PI_PLAN_IN_REVIEW`, set on every spawned review and checked *both* at the call site and inside `dispatchReview` itself. Checking it twice is deliberate: a single guard at the caller is precisely the honour-system shape this ADR rejected for the forgotten `attach`, and the second check means a future second caller cannot reintroduce the recursion by forgetting it. The child also has `PI_PLAN_KEY` cleared, so a review can never adopt the plan it is reviewing as its own.

The other decision the dispatcher forced is what a **dead review** costs. A dead review — no parsable Verdict, a crash, or a wedge past the deadline — leaves the Item in `review` with the reason appended to its note, and **does not spend the Review Budget**. Spending it would let a flaky endpoint escalate work that was never actually judged, which is the opposite of what the Budget is for: the Budget exists to stop *oracle disagreeing forever*, not to punish an Item for infrastructure failures. The deadline itself is 25 minutes, above pi's ~10.6-minute worst-case retry ladder with room for a genuinely long review, and it carries the same coupling ADR 0033 records — raising `retry.maxRetries` or `retry.maxDelayMs` means raising this too.

One race is settled explicitly in favour of the user. A review takes minutes, during which the user may accept the Item or re-route it. The Verdict is therefore applied inside the plan lock and re-checks that the Item is *still* in `review` and *still* on the `oracle` route; if it is not, the Verdict is discarded. Your hand always wins.

ADR 0023 rejected a plan-level route, so a global mode needs justifying rather than assuming. The reconciliation is that 0023 rejected a route that *overrides* per-Item choices; this one only supplies the **default** for an Item that never stated a preference — the case 0023 itself left open by defining an absent route as `user`. Per-Item granularity survives intact: the risky Item and the typo fix can still diverge, and the one-way ratchet still holds, since a default is not an assignment and escalation still only moves toward more scrutiny. That is also why the mode lives in the plan file rather than in `settings.json` or a slash command: the mode is a property of a body of work, one plan may be autonomous while another is not, and it must survive the restarts that have punctuated this work.

**Amended on the visibility cost.** This ADR accepted invisibility for plan-spawned processes and deferred "extract the Task registry" as out of scope. That holds for *reviews*, because oracle is read-only by rule — an unobserved reader can waste time but cannot damage anything. It does **not** hold for **Rework**: a Rework worker has `write`, `edit` and `bash`, so an invisible one is an unobserved *writer*, with no **Mirror Pane** to watch, no `/runs` row, no **Reminder** when it finishes, and — in this repo, which is not under version control — no undo. The user's decision is therefore that observability is a **precondition** of autonomous Rework, not a later nicety. Autonomous Mode consequently ships review-only, which is the safe half, since a failed **Verdict** returns an Item to `active` with findings and a human or orchestrator does the fixing.

**Superseded on the remedy by [0039](./0039-run-directory-is-a-shared-contract.md).** The prescription above — that "the registry extraction must land first" — was wrong about *which* thing to extract. The Reminder that extraction would have been for does not live in the registry, and the surfaces that matter (`/runs`, Board progress, Mirror Pane) are all disk-derived, so what got shared is the Run *directory contract*, not the Task registry. Plan-spawned reviews are now observable, and this ADR's claim that they are invisible by design no longer describes the code. Two further corrections to the reasoning above: the **Reminder is not load-bearing** for safety, since the danger window for a rogue writer is *during* the run and a notification afterwards does not touch it; and observability alone is **not sufficient** to license autonomous Rework, because it is detection rather than prevention — a writer additionally needs an admission cap (the **Review Budget** bounds serial retries per Item, not parallel workers across Items) and either a tool scope without `bash` or a scratch-copy-and-apply-on-pass discipline.

Two decisions run against the obvious choice. First, **`unsure` no longer escalates immediately** — 0023 said it did, and this ADR amends that, because with a **Review Budget** in place an `unsure` retried once still reaches the user if it recurs, so escalating on the first one only spends a user interruption to save a single run. The three tokens stay distinct even though two now share a destination: `unsure` tells a reviser the work may be right but could not be established, which is different guidance from `fail`, and a *missing* token is not `unsure` at all but a dead review, which is retried rather than acted on. Second, **the plan extension spawns the review itself**, outside the Task registry. It can: `agents/oracle.md` is a standalone file and spawning is `pi` in a subprocess, so no import of the subagent extension is needed and the boundary between the two holds. The point is autonomy that does not stop when the orchestrator stops — a review dispatched through the orchestrator can only advance while the orchestrator is running.

**Considered.** *A mode that overrides every route* is the most literal reading of "I do not want to review manually" and was rejected because it silently auto-clears an Item deliberately routed `user`, contradicting 0023 head-on. *No mode at all*, simply routing Items to `oracle` at grooming as 0023 already permits, needs no new concept and was rejected because there is then no single switch to turn autonomy off and the policy lives in the orchestrator's judgement rather than the user's. *Nudging the orchestrator via `sendMessage`* keeps everything inside the existing boundary and was rejected for the reason above; *an honour-system obligation documented on the tool* was rejected outright as the exact shape of the forgotten `attach` in [0030](./0030-task-ids-are-attached-not-created.md), where nothing enforced the step and it silently did not happen. *Extracting the Task registry into a shared module* so reviews appear in `/runs`, get **Mirror Panes** and **Reminders** was rejected as out of scope now, not as wrong — it is the natural fix for the visibility cost below. *Letting the orchestrator perform its own Rework* was rejected on this session's own evidence: two of the confirmed bugs (`board.ts` treating `toolUse` as finished, `restoreScreen` never leaving raw mode) were written *and declared verified* by the orchestrator, then found by oracle. Unsupervised, that same agent revising its own rejected work is the loop's weakest link. *Requiring two independent oracles to confirm a `pass`* was rejected on cost, at roughly ten minutes per review.

**Consequences.** The user can now be absent while Items are cleared, which is the point and also the risk: nothing reads the **Write-up** before an Item reaches `done`, so a `pass` on a review that misread the code is indistinguishable from a good one. The **Review Budget** bounds the damage in time, not in kind. Reviews spawned by the plan extension are **invisible to everything built for Runs** — absent from `/runs` and `subagent_tasks`, with no **Mirror Pane**, no Board progress line and no **Reminder** — and, worse, a wedged review is invisible too, which is the failure that has already bitten this work twice (see the Task-wedge finding: a Run that dies on an unretryable provider error never reaches a terminal state). Autonomous Mode therefore should not be trusted before that wedge is fixed. Delegating each **Rework** to a fresh **Run** buys independence and pays in context: tonight's findings needed the whole session's history to act on, and a fresh worker has only the note. Finally, a per-Item `pass`/`fail` model cannot express "this Item is fine but it broke a neighbour" — tonight one finding implicated two Items at once — so in Autonomous Mode such a finding may clear an Item while the real problem goes unrecorded. That gap is known and unsolved.

**Amended: the gate was in a place the traffic did not go.** The `oracle` default above was applied at exactly one condition — `params.state === "ready"` — on the reasoning that grooming is when a Review Route is chosen. That reasoning is sound and the placement was still wrong, because an orchestrator is instructed to mark an Item `active` when it starts work. The common path is `backlog` → `active` → `review`, which never passes through `ready`, so the default was never applied. Autonomous Mode ran for an entire session with `autonomous: true` on its plan-meta line, the Board rendering its `◇ autonomous` banner, and **all six Items on the `user` route** — every one of them landing on the user's desk, which is the precise opposite of the mode's purpose. Measured across every plan this repo has ever had: 163 of 167 Items on `user`, 4 on `oracle`, and `skip` never used once.

Nothing failed. The mode was stored correctly, reported correctly, and displayed correctly; only the behaviour was missing. That is the failure mode this ADR should have anticipated for itself, having already recorded the plan-meta line's silent deletion — a feature whose *only* symptom is the absence of an effect cannot be verified by looking at it. The rule therefore no longer lives inline in the handler. It is `routeToAdopt(item, nextState, meta)`, pure and exported for the same reason `setRoute` is: an extension is loaded once at pi startup and stays resident, so the live tool cannot be trusted to exercise the code on disk. Its tests assert every state, and both this bug and the ratchet bug below were re-introduced as mutants to confirm the tests actually catch them (5 and 2 failures respectively).

Any **non-terminal** transition now adopts the default. Terminal states are excluded, and that exclusion is load-bearing rather than tidiness: the `done` guard decides whether an agent may clear an Item *by reading its route*, so a terminal transition that backfilled a route would let an Item award itself the very route permitting its own completion, in one call. That is the anti-gaming property of 0023 defeated by the fix meant to serve it.

**The ratchet had to give way slightly, and only where it was never load-bearing.** `routeOf` reports an absent route as `user`, which is correct everywhere it is *enforced* — an Item nobody routed must be cleared by nobody but the user. But `setRoute` used it too, so moving an unrouted Item to `oracle` read as de-escalation and was refused: Autonomous Mode could not adopt the very Items it was switched on for, and "re-route this Item to oracle" was impossible for the 157 Items that had never stated a route. `chosenRouteOf` now distinguishes *absent* from *explicitly `user`*. An Item with no route is unconstrained; an Item with an explicit route ratchets exactly as before. This is 0023's own reasoning applied consistently — that ADR already defined an absent route as `user` while this one already argued "a default is not an assignment" — and the anti-gaming guarantee survives untouched, because an agent still cannot lower a route anybody actually chose.

**Two claims above are now false and are corrected here.** First, "**Rework** is not delegated to a fresh **Run** — not built, and deliberately so" was true when written and was superseded by [0041](./0041-rework-is-done-by-a-fresh-run.md): a failing Verdict now spawns a fresh `worker` Run with the findings, observable as a `pln-` Run, bounded by the shared spawn cap, and committing one revertable commit. Second, and more dangerous to leave standing, the amendment on visibility justified itself partly on this repo having "no undo" because it was **not under version control**. It is under git, and 0041 already relies on that for revertability. A stale risk premise is worse than a stale feature list, because the next reader weighs a decision against a danger that no longer exists.

**Considered.** *Applying the default at creation instead* (`op add` / `op seed`) makes an Item's route visible from birth and was rejected as insufficient on its own: `op add` may carry an explicit route, and an Item created before the mode was switched on would never pick it up. *Gating at `review` instead* — refusing a `user`-routed Item into `review` while the mode is on — forces the decision at the last possible moment and was rejected because a refusal at the end of the work is the most expensive place to discover a routing problem. *Doing both creation and transition* is belt-and-braces and was rejected as two rules where one suffices, since a transition-time default already covers every Item that will ever change state. *Leaving the ratchet strict and hand-editing the plan file* to re-route one Item was rejected outright: the plan tool's own documentation forbids editing the file directly, and a workaround that bypasses the tool is how invariants stop being invariants. *Removing the ratchet entirely* was offered and declined by the user — it would let an agent lower its own scrutiny after discovering how painful review would be, which is the one thing the ratchet exists to prevent.

**Consequences.** Autonomous Mode now actually fires, so the full loop — oracle review, then a fresh writer Run on a failing Verdict — becomes live for the first time on any plan with the mode on. Everything this ADR's original Consequences warned about therefore starts applying *in practice* rather than in principle, in particular that nothing reads the review Write-up before an Item reaches `done`: a `pass` from a review that misread the code is indistinguishable from a good one, and the user has explicitly accepted that trade. The Review Budget still bounds the loop to one Rework per Item before the route ratchets to `user`. One asymmetry is worth keeping in view: `routeOf` and `chosenRouteOf` now differ in exactly one case, and a future call site that reaches for the wrong one is a silent bug in either direction — enforcing on `chosenRouteOf` would let an unrouted Item self-clear, while ratcheting on `routeOf` would restore the bug fixed here.

**Amended again: switching the mode on adopts the default for Items that already exist.** Fixing the gate above fixed every Item that would *move* from then on, and reached none of the Items already parked. `routeToAdopt` fires on a transition, and an Item sitting in `review` never makes another one — so five Items stayed unrouted, waiting for a reviewer nobody would ever dispatch, in a plan whose banner said `◇ autonomous`. The user found them, which is the wrong way for this to surface. `op autonomous` therefore backfills: turning the mode on adopts `oracle` for every unrouted non-terminal Item, and dispatches a review immediately for any of them already in `review`, because dispatch normally rides on the transition *into* `review` and that has already happened for these.

This needs reconciling with two earlier refusals rather than assuming, since both look like this on the surface. ADR 0023 rejected a plan-level route that *overrides per-Item choices*, and this ADR rejected "a mode that overrides every route" because it "silently auto-clears an Item deliberately routed `user`". Both objections are about overruling a decision somebody made. The backfill touches **only Items with no route at all**, which is an inferred default and never a choice — the same absent-versus-explicit distinction `chosenRouteOf` already draws for the ratchet. An Item explicitly routed `user` is left exactly as it was, which is the property that keeps this on the right side of both refusals, and it is the assertion most worth protecting in the tests: a mutant that drops the unrouted check fails five of them, the explicit-`user` case among them.

**Considered.** *Leaving it* is defensible — the stranded population was created by a bug now fixed and cannot grow — and was rejected because "turn on Autonomous Mode" plainly reads as applying to the plan, so the next person to enable it on an existing plan hits this again. *A separate maintenance op* (`plan requeue`) is more explicit and was rejected as a second concept for something the mode should simply mean. *Backfilling on every plan write* rather than at switch-on would also catch an Item that predates the meta line, and was rejected because a route would then change under an Item at moments nobody asked for anything, which is exactly the invisibility this ADR keeps being bitten by.
