# subagent-herdr — herdr-backed subagent delegation

Owns the `subagent` / `subagent_tasks` tools (advertised by the orchestrator prompt). Each delegation is a new herdr tab in the orchestrator's workspace running a native `pi` TUI, plus a run directory under `agent/subagent-runs/`.

**Delegation is event-driven: there is deliberately no blocking wait.** The orchestrator delegates, ends its turn, and is woken by a *notice* the child types into its pane (`herdr agent prompt`) when the child reports or finishes. A blocking wait is what the module used to do, and it made mid-run messaging structurally impossible: the wait ran inside a tool call, so the parent was streaming, so a child's report could only queue as a follow-up and stayed invisible until the child was already dead. Do not reintroduce one.

**The briefing is delivered as `deliverAs: "steer"`, and that word is load-bearing.** pi's agent loop drains its two queues from different places (`pi-agent-core/dist/agent-loop.js`): steering at the end of *every* turn inside `while (hasMoreToolCalls || pendingMessages.length > 0)`, follow-ups only *after* that inner loop exits. So a follow-up reaches an orchestrator that is still calling tools only once it has stopped calling them — i.e. once its turn is already over. Delegating and then continuing to work (a read, a grep, another spawn) kept the loop inside the inner `while`, where the follow-up queue is never polled, so a finished child was unreachable for the rest of the turn however long it lasted. Steering cuts in at the next turn boundary, after the current tool results are in context and before the next LLM call, so it never splits a `tool_call`/`tool_result` pair. Interrupting is the intent: a subagent's answer is new information that should redirect the loop, not queue behind the work it invalidates. The idle path is untouched — `deliverAs` is only consulted while `isStreaming`.

The queue structure and `deliverAs` were last re-verified against an installed pi in the 1.0.x
line; `index.ts`'s comment still cites the original 0.99.2 measurement, and the running pi is
now **1.4.0** (measured 2026-10-28). Two revisions of this paragraph disagreed about which 1.0.x it was, so re-measure
against the installed bundle rather than trusting any version written here.

## CONVENTIONS (local)

- **The contract is spelled once.** The child is launched with `-e` and imports only shared modules (`rundir.ts`, and `../lib/agents.ts` for agent definitions) — run-dir paths and JSON shapes change there, never in both halves.
- **Pane and tab ids come from herdr responses, never predicted.** The *agent name* and the run id are the opposite: constructed locally (`herdrAgentName` = `<agent>-<runId>`, `makeRunId`), with herdr's `agent_name_taken` the collision detector.
- **`herdr.ts` never throws.** Every entry point resolves a structured value; the delegation surface must not take down the session hosting it.
- **A pane is gone only when herdr says `agent_not_found`.** `probeAgent`/`probeFromCall` are three-way: `gone` (that code alone — measured on herdr 0.9.1), `unreachable` (timeout, crash, malformed reply, any other code), or a live `state`. An unreachable herdr says nothing about the child, so the run stays `running` and the next read retries; `status`/`result` name it (`unreachable (…)`), never `[pane gone]`. There is deliberately no two-way variant: a `getAgent` whose `null` meant both was what classified live runs `failed` on a herdr hiccup, and it was deleted rather than kept for compatibility.
- **Pinned to the measured behaviours in `herdr.ts`'s header** (baseline 0.9.0, plus the 0.9.1 `agent_not_found` measurement and the 0.9.3 prompt-stall window — `agent_prompt_stalled` when an accepted submission does not reach `working`/`blocked` within 5,000 ms). Re-verify the "measured behaviours" in `herdr.ts`'s header against the installed version before changing any of them.
- **Completion is two signals:** the `subagent_done` tool (injected into every child's allowlist) or a clean `agent_end`. A failed turn writes no sidecar, so the parent classifies from its absence.
- **Every child's allowlist also gets `todo`** (`TODO_TOOL_NAME`, appended by `buildChildArgv` beside the two handshake tools, deduped). A plain `--tools` list *replaces* pi's selection, so without the append no agent definition had a checklist at all; it is launch policy, not a per-frontmatter capability, and it writes no files, so a read-only agent stays read-only. `todo.ts` registers only where `PI_SUBAGENT_RUN_ID` is set; the orchestrator has `kanban/` instead, whose side pane is split off the orchestrator's own pane with the generic primitives in `herdr.ts` (`splitPaneOf`, `paneExists`, `paneRect`, `runInPane`, `closePane(…, timeoutMs)`).
- **Neither completion signal fires without a visible answer, and one predicate decides what that means.** `qualifiesAsAnswer` (in `rundir.ts`, beside the paths and the notice grammar, because it spans the same seam) is applied by the child's gate *and* by the parent's `extractRunResult`: visible assistant text only, and under a `<result>` contract a complete `<result>…</result>` element. **Whether the contract applies is read off the run's own `system-prompt.md`** rather than hardcoded or declared in frontmatter — every agent in `agent/agents/` ends its prompt with "Only what is inside `<result>` reaches the orchestrator", the three `technical-analysis` journal agents do not, and a future one need not. Thinking is never consulted: reasoning does not reach the orchestrator, so a report composed there is not an answer. The gate exists because both signals were taking the model's word for something it got wrong in 9 of the 37 recorded `explorer` runs, plus 5 of the 64 `librarian` ones — the report went into a fabricated `subagent_done` argument (the schema is `Type.Object({})`, and typebox accepts extra properties, so the call was *valid* and the payload discarded), or into thinking, or nowhere, and **both ends recorded a success**. `subagent_done` is refused `MAX_REFUSED_COMPLETIONS` (2) times and then allowed through — a child that can never finish is worse than one that finishes badly — and a silent clean `agent_end` gets exactly one `sendUserMessage` nudge before completing as before. Do not make either bound unbounded, and do not let a refusal write the sidecar: the sidecar is what makes the parent call the run `done`.

- **A card child owes the board a list, not just an answer.** `PI_KANBAN_CARD` (shape `k<n>`) names the kanban card the delegation does; `cardOf` is the one truthiness check in the child — an empty string is "no card": no gate, no ask tool, no prose. For a card child, `child-done.ts` replays the branch's newest `todo` tool result's `details.state` through the shared `parseTodoState` (`../lib/todo.ts` — the same rule the board's `kanban/runs.ts` applies, not a restated copy; `todo.ts`'s own rebuild is looser); the replay is lazy, at both call sites (`subagent_done`'s execute and the `agent_end` handler), so only a card child pays for it. `cardAccounting` decides: an empty list (the child never built one from the card) or open items is unsettled — `blocked` is *not* open, it is a declared waiting state with a note. The gate shares the answer gate's counter: a `subagent_done` with a qualifying answer and an unsettled list is refused (one bad call consumes one of the `MAX_REFUSED_COMPLETIONS` refusals, not two), and when *only* the card list blocks the refusal is `cardDoneRefusal` alone, with its own accurate opening — composing the answer guidance's "no answer" opening and "receives nothing" closing would be lies, and an instruction to re-emit the answer would strand the report (see the parent-side salvage bullet). A card child that ends its turn cleanly with a qualifying answer and an unsettled list gets exactly one follow-up turn (`cardOnlyNudge`, through the same one-shot nudge slot, no sidecar), and the next clean end finishes the run whatever the list state; a card child that ends *without* an answer gets the answer nudge with the `cardNudgeTail` appended — **only when the list has open items**: a settled list gets no tail, since `openItemsClause([])` is the empty string and the sentence would read "…:  are still open" while spending the one-shot slot on nothing. The briefing for a finished run carries its final checklist as a `todos: 2/3 done, …` line under the header (counts ride `extractRunResult`'s single pass through the shared `parseTodoState` — no second read, no claim on the degraded block, whose result read is exactly what failed). The `subagent_ask` tool is registered for card children only, with its own `MAX_ASKS_PER_RUN` (3) budget spent only by an ask that actually posted — a no-run-dir ask is a launch misconfiguration and does not burn one of the three.
- **The kanban board's run progress is a disk read, woken by a process-local event.** `kanban/runs.ts` tails the child's session JSONL (bounded ladder 32 KB → 512 KB → 4 MB on a miss, `size:mtimeMs`-stamped cache dropped on **both** terminal paths (meta-terminal and the `.exit` sidecar); measured over 450 transcripts in 443 recorded run dirs: 37 carry a todo snapshot, 15 sit >32 KB from EOF, p90 ~1.0 MB, max ~2.8 MB, largest single line ~1.0 MB — the 4 MB cap covers 37/37; a step that already covered the file stops the ladder (no byte-identical re-reads on the 1 s poll), and every ladder miss arms a per-transcript memo at the **newline boundary** of the window it read: the transcript is append-only, so growth re-scans only the appended region (at any transcript size, including a first read past the cap — board restart mid-run), and a torn tail is re-read whole next pass; a size that goes DOWN, a size-equal rewrite, or a stamp that moves without the size moving (a Nextcloud sync restore) invalidates the memo and the ladder re-proves from scratch; bytes farther from EOF than the first read's 4 MB tail are never reached), so a first-pass miss is evidence the window was too small, not that the child never built a list) and renders the counts under a live run's line (`RunInfo.todos`; `kanban/lib.ts` `cardLines`/`compactLines`). A terminal run's entry is dropped from the cache and its line vanishes — the board is about work in flight, not history. `kanban/index.ts` re-reads on `RUN_TODOS_EVENT` (defined in `../lib/todo.ts`, because it is a contract between two siblings that must not import each other for a name), which this module emits from `armFlush` (after a flush) and `runLivenessTick` (every 60 s) — both in the orchestrator process, where the kanban extension lives; the child's process has no board to wake.
- **A response truncated by the output token limit is continued, not finished.** `stopReason: "length"` means the model's output budget ran out mid-answer, and nothing in pi's agent loop tells it to go on — the run would sit idle in its pane, and a result-contract child truncated mid-`<result>` can never settle, because the parent's completion predicate demands a clean, unsalvaged answer. So the child's `agent_end` handler detects the truncation and sends a continuation nudge (`sendUserMessage(…, { deliverAs: "followUp" })` — the same path as the answer nudge, and pi's `_handlePostAgentRun` starts a fresh run from the queued follow-up), bounded by `MAX_CONTINUATIONS` (3) and sent only while no qualifying answer exists: a bound-spent or already-answered truncation finishes the run the way a clean end does, so the parent reads whatever the transcript carries and labels a short answer salvage. The card gate rides this branch the same way it rides a clean end, and it never lies about the answer: a truncated card child with a qualifying answer and an unsettled list gets exactly one `cardOnlyNudge` before finishing (the one-shot `nudged` slot, no sidecar); a truncated card child with **no** answer and open items gets the card tail appended to the continuation prose (a settled list gets no tail) — `cardOnlyNudge`'s "your run has an answer" opening must never ride a no-answer case, and the no-answer slot is reserved for the answer nudge that recovers a stranded report. Do not make the bound unbounded (a report longer than the model's output budget would loop forever) and do not let a continuation write the sidecar — the sidecar is the done classification, same rule as the refusal.
- **Parent-side salvage is deliberately looser than the gate, and that asymmetry is load-bearing.** The gate asks "may this run finish?" while the child can still fix it; salvage asks "is there anything worth forwarding?" once the alternative is `(no final answer in transcript)`. So `extractRunResult` falls back to the done call's own string arguments (preferring `message`) and then to an earlier message, judged by `qualifiesAsSalvage` — a complete `<result>`, or any text past `SUBSTANTIAL_ANSWER_CHARS` (400). That bar is set from the real runs: the three stranded reports were 7.5 KB, 9.2 KB and 17.4 KB while the filler lines left in their place were 48, 62 and 63 chars. **Requiring even an opening `<result>` here was tried and measured — it discards two of the three**, which carried no tags at all; a model that spends its budget on a tool argument gets truncated. Salvage proceeds in four steps — strict answer, then done-call arguments, then substantial text, then *any* visible text as `non-conforming` — and each is labelled in the briefing (`truncated-answer`, `earlier-message`, `done-arguments`, `non-conforming`) so a recovered or inadequate report is never mistaken for a clean one. **The four steps and their inclusive bounds are a regression gate, not a preference:** an earlier draft keyed the search on the last *entry* and started the looser pass *below* it, which lost 47,678 chars across 20 of the 164 recorded runs (8-15 KB reports in `sub-c62b`/`sub-1a09`/`sub-db10`, and a 15,430-char answer replaced by a 565-char interim note in `sub-7864`) while all 190 tests passed — because every fixture happened to have a `subagent_done` call and the dominant real shape has none. Re-run the full replay over `agent/subagent-runs/` after touching this function; the invariant is **zero** answers lost or shortened against the previous implementation.
  - **Which transcript the answer comes from is its own measured rule.** A resumed run dir holds more than one session file of its own run (3 of 443 recorded dirs — the "18" a naive `*.jsonl` glob counts includes foreign-id transcripts); `findSessionFile` takes the transcript the `.exit` sidecar settled — that IS the run's answer — and a *newer* transcript with no sidecar (a post-completion resume) must not displace it: pure newest-wins measured as losing `sub-2ea3`'s 17.4 KB answer, replayed over all 439 recorded runs. While nothing is settled (the run is live) the newest wins — the same rule the board's progress reader uses, so the answer and the progress line come from one transcript during the run.
- **The notice grammar lives in `rundir.ts` and is parsed strictly.** The parent *swallows* every input that matches it, so a loose pattern would eat a human's typing. Both ids are constrained (`sub-` + four hex; herdr's agent-name rule), and anything that does not match is passed through untouched.
- **A child's prompt is its definition body plus whatever `skills:` names.** pi builds `## Available Skills` for the orchestrator only, so without that key a subagent cannot know any skill exists. An agent that declares no skills gets a byte-identical prompt, which is what makes the feature safe to leave off. Discovery failing costs the catalogue, never the launch.
- **`skills:` resolves against pi's own catalogue, not just `agent/skills/`.** The `before_agent_start` hook captures `systemPromptOptions.skills` into `piSkillCatalogue` and `skillEntriesFromPi` maps it; `spawnRun` prefers that over scanning the skills dir. That is what lets an agent declare a skill from an installed package (`test-driven-development`) or a project-local `.pi/skills` at all — `selectSkills` drops unknown names by design, so before this such a declaration resolved to *nothing* with no error, and the agent merely looked like it was ignoring its skill. Taking pi's already-resolved list also means the human's resource filters (`-skills/foo`, include-lists, `autoload: false`) are honoured for free: a child can never be handed a skill the orchestrator was denied. **Do not re-read `settings.json` to rediscover this** — that is a second parser of a format pi owns, and the first draft of this feature had already drifted from pi on pinned `git:…@ref` sources and on per-skill excludes. Keyed on the *directory*, since `selectSkills` matches `dir` and frontmatter `name` may differ. `disable-model-invocation` skills are retained: pi strips those only when rendering the orchestrator prompt, and an agent that names one should get it. Scanning `agent/skills/` remains the fallback for a spawn before any turn has started.
- **`fallback_models` feeds the router, not a launch loop.** `childFallbackChain` builds a non-empty deduped canonical chain from the agent's `model` and `fallback_models` declarations (or from the explicit `model` on the delegation call, which yields a singleton). That chain crosses to the child as `PI_FALLBACK_CHAIN`, and the child always launches on `fallback/auto` — the model-fallback router resolves the chain at runtime and hops entries on provider failure. One launch attempt per child: with a non-empty chain the router registers, pi starts and accepts the prompt, and a chain the router cannot serve fails at the first request — so a dead entry shows up in the child's transcript, not in the launch. The env var's name, the router's id, and the whole item grammar are imported from `../model-fallback/lib.js`, never restated here. A child with no valid reference at all (no `model`, no `fallback_models`, all malformed, or naming the router itself) gets no chain and `admitSpawn` returns an actionable error, which `spawnRun` hands back before creating a run dir.
- **Chain entries may be `ref|level`, pinning a thinking level for that model.** The item grammar is owned by `../model-fallback/lib.ts` (`parseChainItem`/`formatChainItem`); this module only applies it. `childFallbackChain` canonicalises entries through the grammar (so a pin crosses the process boundary verbatim) and drops what the grammar rejects, so the chain advertised in the env var contains only entries the child's router will serve. Dedup is by ref, case-insensitively, first occurrence winning. **Any non-empty chain is valid** — the router registers for every non-empty `PI_FALLBACK_CHAIN`, including a single unpinned entry, because the child always launches on `fallback/auto` and needs at least one resolvable entry.
- **Ancestry is accumulated by processes, not trusted from models.** `buildChildEnv` stamps `PI_SUBAGENT_LINEAGE` (the agent-name chain, oldest first) into the child; `lineageRejection` reads it back one process later and — through `admitSpawn` in `lib.ts`, which `spawnRun` calls first — refuses *before* a run dir, registry entry or pane exists. Two rules, cycle first: an agent in its own ancestry is refused (so `librarian → librarian` cannot happen), then `callable_by` is honoured (so `summarizer` is the librarian's alone). An empty lineage is the human's orchestrator and may spawn anything; any other caller must be named in the callee's `callable_by` or the callee must declare `any` — an absent key is orchestrator-only, never public. The guard, `parseLineage`/`formatLineage` and `spawnableAgents` live in `../lib/agents.ts` (re-exported from `lib.ts`), and both `spawnRun` and `dynamic-prompt.ts` take their roster from its `delegationRoster`, so the prompt advertises exactly the roster this guard permits. `spawnRun` hands `.all` to `admitSpawn`, which looks the requested agent up there (so a known-but-forbidden agent gets `lineageRejection`'s specific refusal rather than "Unknown agent") and lists only what this lineage may spawn, under normal non-system rules, as the "Available agents"; the designed fleet graph is pinned by `lib.test.ts` ("the fleet delegation graph") and documented in `agent/AGENTS.md`. This replaced a numeric `MAX_DEPTH`, which had to be tuned and whose obvious value of 1 refused the orchestrator's own child; ancestry needs no constant because the roster is finite. `../lib/dotenv.ts` records the fork bomb this interlock exists to prevent.
- **A `done` notice is only a prompt to look, never the evidence.** The completion *signal* is what classifies a run: the `.exit` sidecar on disk, **or** a *clean* transcript answer (`answered` and `salvagedFrom === undefined`). That predicate is spelled once, in `run-lifecycle.ts`, and every classification — running reads, settle retries, revival — calls it. A salvage (`earlier-message`/`done-arguments`/`truncated-answer`/`non-conforming`) is deliberately **not** a signal: it proves the child produced text, not that it stopped, so a live pane is not closed on it alone. Bare `answered` is too loose, because `extractRunResult` sets it for the non-conforming "any visible text" salvage. A notice that never lands costs promptness, not correctness — which is why every read path goes through `lifecycle.read` first. A herdr pane reporting `done` is **idle/readiness only** — it means "ready for input," not "run finished" — so it never classifies a run by itself: a live `done` pane is a prompt to re-read the disk/transcript, and the run finishes only when a real signal is present.
- **Terminal writes have a fixed order.** `done` (and a late completion): mutate → `saveMeta` → close the pane best-effort. `failed`: mutate → `saveMeta`, **never close** (see ANTI-PATTERNS). `cancelled`: mutate → `saveMeta` → close best-effort — persisting *before* the destructive close is deliberate, so a cancellation survives a hung or failed close. A launch failure: pane ids → `failedAttempts=[attempt]` → status/timestamp → save, never close. `saveMeta` stays best-effort.
- **A run is registered before its pane exists, and that launch window is not evidence.** `spawnRun` puts the record in `runs` (so it is statusable and cancellable at once) and its id in the process-local `launchingRunIds`, removed in a `finally` once the launch settles. The lifecycle's injected `isLaunching` makes a paneless in-flight record an unchanged `{kind:"launching"}` observation — no extract, no settle, no transition — so no sweep, tick or query can fail it as `no-pane` (`status` shows `herdr: launching`; `message`/`interrupt` say `still launching`). Measured: one liveness tick ~1.15 s into a four-way fan-out failed all four live explorers and spawned an `ended-without-result` health check on each. The marker is never persisted, so a paneless `running` record in a fresh process (stranded by a crash or a partial write) still settles as `no-pane`. **Every launch exit that leaves a still-running record goes through `lifecycle.launchFailed`** — including a failed system-prompt write — because a paneless `running` record left behind once the marker clears is exactly what the next sweep health-checks. A failed `promptAgent` (herdr's 5 s accepted-submission window answering `agent_prompt_stalled` — measured in five real stalled launches) is recovered by a **bounded retry**: up to `PROMPT_RECOVERY_ATTEMPTS` (3) Enter sends, each followed by a 5 s `waitAgentWorking` observation, which keeps the original 15 s aggregate recovery budget; success exits the loop immediately, a superseded run exits at its next `superseded()` check, and a launch that cannot start fails with the pane kept as evidence. A cancel that wins the window wins outright: `launchRegisteredRun` re-checks `rec.status` after every await, and a superseded launch closes whatever pane it got (even a failed attempt's), never calls `launchFailed` (it rejects a non-running record), never re-saves meta, and returns `ok:false`. The success tail — status check, pane ids, `saveMeta` — is synchronous after the last await.
- **A flush sweeps the registry, so a fan-out that finishes together produces one response.** The ledger's `flush` runs one `lifecycle.sweep` before composing: it reconciles every owned running run (concurrency 8) and folds any that have already finished into the same briefing. The ledger's briefed set (`briefedRunIds`) suppresses a later notice for an already-briefed completion, and the ledger serializes `flush` bodies internally so overlapping timers cannot race the dedup set. The factory owns only the timer: `armFlush` re-arms one coalesce timeout to the deadline the ledger returns and sends whatever text `flush` returns. `steeringMode: "all"` in `agent/settings.json` is the backstop: if two briefings ever land in the steering queue simultaneously, pi drains both into the same next turn.
- **The child's notice is `spawn`ed detached.** `closeOwnPane()` kills the child's process group moments later, and a delivery still attached would die with it.
- **herdr agent names are unique among *live* agents server-wide (a name frees when its agent exits or is released), so children register as `<agent>-<runId>`** (`herdrAgentName`). The bare definition name let the first live `librarian` own it and made every concurrent sibling unlaunchable with `agent_name_taken`. The *bare* name still goes in the notice grammar and `PI_SUBAGENT_AGENT` — only the herdr registration is scoped. herdr's 32-char ceiling applies to the **scoped** name, which leaves a definition name 23.
- **Validate the *scoped* name, never the definition name** (`childNameRejection`). Scoping costs 9 chars, so a 24-char definition name is legal alone and illegal once scoped — checking the bare string let that fail late, after a pane was opened.
- **A herdr refusal arrives on stderr with a non-zero exit**, not on stdout (measured, 0.9.0). `herdr()` parses the `{"error":{"code"}}` document off *either* stream; a catch branch that only reported "herdr exited 1" is what disguised `agent_name_taken` as a launch timeout for five runs. `classifyExecFailure` is pure and tested because the bug was *not looking* on the stream that carries the code.
- **The parent-side health check is a diagnosis layer, not a second completion mechanism.** A `stalled` notice (the child watchdog's one-shot signal) is consumed by the input hook before it reaches the orchestrator: on success the extension spawns a read-only `healthcheck` child whose task (`buildHealthCheckTask`, `lib.ts`) names the target run, its run directory, its original task (fenced in a code block so a task containing `<result>` or `## Recommendation` cannot blur the output contract), and the trigger detail. An `ended-without-result` target (a finished run whose `extractRunResult` returned `answered: false`) is deferred: its no-answer block is held back while the health check runs, and the health check's completion (done, failed, or cancelled) delivers both blocks in one steering briefing. A health check that cannot launch renders the no-answer block immediately. **Cancelled runs skip the gate entirely** — a deliberately killed run is terminal and gets its block rendered at once without a health check. The ordinary `.exit`-sidecar completion path and the answer gate are untouched. Deferral is derived from the runs map, not a persistent set: a target is deferred iff a health-check record for it is currently `running`. The release is carried by a **done notice for the health check itself** — enqueued by the liveness tick when the tick first finds the check terminal, and by the `cancel` action when the orchestrator cancels it — because a notice is what wakes the orchestrator: a terminal check whose notice never lands releases nothing.
- **Health-check spawning is guarded, and `healthCheckOf` is the single persistence key.** Two guards: at most one *running* health check per target — the `runningHealthCheckFor` scan reuses an in-flight record, and a **synchronous in-flight marker** (the ledger's `healthCheckInFlight` set) is added before the first await in the ledger's `requestHealthCheck` so two concurrent entrants cannot both see an empty map and both spawn; the marker is cleared in a `finally` whenever the injected `spawnHealthCheck` collaborator (the factory's `spawnHealthCheckRun`, a bare `spawnRun` call) settles (success hands off to the map, failure leaves the record terminal), so no path leaks it. A health check is never health-checked (recursion refused by `target.agent === "healthcheck"` or a string `healthCheckOf`). A *terminal* check does not block a new trigger: the stall and no-answer triggers ask different questions, so a target whose stall was diagnosed can still get a fresh check when it later ends without an answer — the in-flight scan prevents only concurrent duplicates. Every read site goes through `healthCheckOfId`, which treats a non-string `healthCheckOf` as absent — matching `isRunRecord`, so a corrupted value can neither trip the recursion guard nor key a bogus deferral. `healthCheckOf` is persisted in `meta.json` and validated by `isRunRecord`. The `healthcheck` definition declares `callable_by: orchestrator`, so no agent may delegate to it by hand; the programmatic spawn (`spawnRun` with origin `{ kind: "system-health-check", targetRunId }`) is the only one for which `admitSpawn` passes `lineageRejection(..., { system: true })`, which skips `callable_by` but keeps the cycle rule — so a nested process (a `worker` whose `reviewer` stalls) still gets its health check.
- **The liveness backstop is a non-blocking, overlap-guarded 60-second reconciliation tick, registered only in the orchestrator process.** The `setInterval` (with `unref`) that calls `ledger.tick` (then `armFlush` on the returned deadline) is wrapped in `if (!process.env.PI_SUBAGENT_RUN_ID)`: children load this module too (they get the `subagent`/`subagent_tasks` tools) and share the on-disk registry, so an unguarded child tick would reconcile records it does not own — closing siblings' panes (destroying scrollback evidence), overwriting siblings' `meta.json`, and injecting sibling briefings into the child's own session, and it can even mark the child's own record failed (herdr's `done` means "ready for input"). The guard's scope is the tick only: it does not prevent children from spawning or querying subagents — those paths are intentionally left open. The guard matches `todo.ts` (`if (!process.env.PI_SUBAGENT_RUN_ID) return;`) and `kanban/index.ts` (`if (process.env.PI_SUBAGENT_RUN_ID) return;`). The tick runs **one `lifecycle.sweep`** over the owned records — the same path as the flush sweep — which both reconciles running records and examines failed ones for revival; already-briefed *running* records are excluded so they are not re-collected. It acts only on records that transitioned to a terminal status: answered runs get a done notice enqueued, unanswered non-healthcheck runs get a health check spawned (done notice enqueued only if the spawn fails), and finished health checks get a done notice enqueued (to release any deferred target). That sweep's **`failed → done` revival** is bounded inside the lifecycle: a candidate must have actually launched (a launch failure — `failedAttempts` present — is never revived), its terminal time (`finishedAt ?? startedAt`) must be within `6 * 60_000` ms, and its session file's size/mtime stamp must have changed since the lifecycle last examined it (the first examination counts as changed) — so an unchanged failed run costs one `stat` per tick, not a transcript read, and history is not re-read after a restart. A revival is reported as cause `late-completion`, and the ledger (not the lifecycle) clears its briefed set for that id, so a late real answer can correct an already-delivered false failure. The tick also runs a **stranded-release scan**: a terminal, non-briefed target whose release was lost (its terminal health check's done notice never landed — `session_shutdown` drops the pending batch) gets the release re-enqueued, and that re-drive is gated twice — **by age** (a check whose terminal transition is older than `6 * LIVENESS_BACKSTOP_MS` is not re-enqueued, so a restart does not re-brief every historical terminal pair on a fresh briefed set) and **by attempts** (`MAX_DEGRADED_RELEASE_ATTEMPTS = 3` degraded deliveries per check whose target block degraded — exactly 3, because the ledger serializes the flush that increments the counter (only for a degraded briefing it actually returns) with the tick that reads it; the ledger's `degradedReleaseAttempts` counter; when the bound burns on the next tick, both ids are marked briefed and the last degraded block stands as the final delivery, so a persistently unreadable target cannot wake the orchestrator every 60 s forever). The ledger guards `tick` against overlap so intervals never run two sweeps at once. The interval and the coalesce timeout are cleared on `session_shutdown`, then `ledger.shutdown()` makes later `enqueue`/`flush`/`tick` calls no-ops; the input hook, the backstop and the `cancel` action all wake through the same `armFlush(ledger.…)` path, so every notice is coalesced and deduped the same way. The compose-failure fallback in the ledger's `flush` is also a release path: when the full compose throws, the catch marks a terminal health check briefed and names its target in the degraded text — registered targets by id/agent/status, unregistered ones (no runs-map entry) by bare id — so the pair retires together and the invariant "HC briefed ⇒ target released" holds on that path too.
- **The run dir is global; ownership is per-pane, and only the owner sweeps.** `~/.pi/agent/subagent-runs` is shared by every pi process, and `loadRegistry` loads every record into every process's map — so `ownerPane` is what tells a process its own records apart from every other session's: each new record persists it (the spawning parent's herdr pane, stamped from `HERDR_PANE_ID` at spawn, before `runs.set` and `saveMeta`), and only that pane's process may *autonomously* act on the run — the flush sweep, the liveness tick, and the stranded-release scan pass only owned records to `lifecycle.sweep`/the scan, the scan also requires the terminal check it re-drives to be owned by the same pane as its target, and the briefing's "Still running" tail names only owned runs. Legacy records (no `ownerPane`) and non-string ownership are **loadable but unsweepable**: they stay globally queryable — `list`/`status`/`result`/`message`/`interrupt`/`cancel` never filter on ownership for visibility, and `status`/`result` report a foreign record's on-disk state without reconciling it (a `lifecycle.read` mutates: it sets the record's terminal status, may close the pane, and saves meta); the answer says so too, so the orchestrator can tell it from a probed one — a `result` query for a foreign or legacy running record carries a `[not probed: …]` marker ("no owner recorded" for legacy, "owned by another session" for foreign), and a `status` query's details carry `owned: false` for the record — but are never swept, including a stale legacy `running` record whose owner pane is long gone (a process without a known pane owns nothing, so its autonomous sweeps are no-ops). A notice explicitly addressed to this pane is evidence of ownership, so direct batch-notice processing is unfiltered. If the owner pane is gone, the run is **orphaned until a process starts in that pane again** — inspect it with `subagent_tasks` rather than expecting reassignment.
- **The `interrupt` action on `subagent_tasks` performs a bounded handshake: reconcile → Escape → bounded idle wait → replacement prompt.** The reconcile runs first because an Escape typed into a pane whose child already finished goes nowhere, and a run that is `done` must be reported as `done`, not "interrupted". The idle wait (`INTERRUPT_IDLE_TIMEOUT_MS = 30 s`) makes the prompt safe: pi's bash tool kills its process tree on abort, so once the pane reports `idle` no streaming response or tool call is mid-flight. **After a successful `sendPrompt`, the record is reconciled once more** (failure-tolerant) so a child that finished between the idle wait and the prompt is reported by its real status rather than stale `running`. Unlike `message` (which queues without aborting) and `cancel` (which kills the pane), `interrupt` leaves the pane alive to do the replacement work. `interruptRun` is exported so the test can drive it with a stub `InterruptEffects` (whose `read` is `lifecycle.read`). The `cancel` action goes through `lifecycle.cancel` (persist, then close) and has one wake side effect of its own, fired only when the record actually transitioned (a repeated cancel enqueues nothing), threaded through the `DispatchEffects` seam: cancelling a health check enqueues its done notice (the release that carries the deferred target's block through the ordinary coalesced, deduped path — the same notice the liveness tick enqueues for a finished check), while cancelling a non-health-check run enqueues nothing, because the orchestrator already knows it cancelled.

## ANTI-PATTERNS

- Hand-writing run-dir paths, JSON shapes, or the notice grammar in `index.ts`/`lib.ts` *and* `child-done.ts` — the drift this module was refactored to kill; `rundir.ts` exists because nothing else would have caught it.
- **Adding any form of blocking wait, poll loop, or sleep-until-done to the parent.** It re-breaks mid-run messaging for the reason described at the top of this file. Ending the turn *is* the wait.
- Widening the notice regex to be "more forgiving". It decides what the orchestrator silently eats from its own input stream; a false positive loses a user's message.
- Closing a failed pane "to tidy up" — herdr destroys scrollback when a pane closes, and the scrollback is the failure evidence.
- Treating `agent read` as JSON — it is the one herdr command that prints raw terminal text, not a JSON document.
- Registering a child under its bare agent name, or otherwise making a herdr identity that two live children could both want. Names are as unique-by-construction as pane ids.
- Flattening a herdr error code into a generic message before the launch attempt classifies it. `agent_name_taken` and `invalid_agent_name` are closed and reported without a pane id — herdr refused the name before pi ever ran, so there is no scrollback to keep and no model retry that would help; reporting a pane id would make the refusal read as a dead model.
- **Switching the briefing back to `deliverAs: "followUp"` so it "waits politely" instead of cutting into the orchestrator's tool calls.** That reads as courtesy and is actually the dropped-wake bug: the follow-up queue is only polled after the inner tool-call loop exits, so the briefing is unreachable until the turn ends on its own. Politeness here means a finished subagent the orchestrator never sees.
- **Letting a refusal or a nudge write the `.exit` sidecar "so the parent knows what happened".** The sidecar *is* the done classification; writing one for a run still being asked for its answer hands the parent a success with nothing in it, which is the original bug with extra steps. A refused `subagent_done` performs no side effects at all.
- **Making the answer gate a second predicate, or hardcoding the agent roster it applies to.** There is one `qualifiesAsAnswer` in `rundir.ts` and both halves call it — **and one `visibleTextOf` beside it**, because *what text is judged* is as much of the contract as the rule. Both were briefly duplicated in `child-done.ts`, and the copies had already diverged on string `content` before they were merged: the child could pass its gate on a message the parent read as unanswered. `lib.test.ts` pins them to the same function identity.
- **Tightening parent-side salvage to match the gate.** Measured: it discards two of the three real stranded reports. The gate and the salvage answer different questions at different times; see the convention above before "unifying" them.
- **Adding `additionalProperties: false` to `subagent_done`'s schema to reject a fabricated `message` argument.** Tempting, and it moves the failure earlier — but a schema rejection is retried by the model with no useful guidance and no bound, whereas the gate explains the mistake and gives up after two. The permissive schema is also what makes the parent's argument salvage possible for runs already on disk.
- **Replacing the bounded launch-time Enter recovery with a single recovery Enter, or widening it into an unbounded or multiplicatively longer retry budget.** The single Enter is what stranded five real launches in `agent_prompt_stalled` (task text left sitting in the child's editor, the run idle, never starting); the bound exists because each observation costs one of herdr's 5 s stall windows — three of them keep the original 15 s recovery budget exactly. A lost keypress is a transient TUI race, not a model failure: retry the keypress, do not retry the launch.
